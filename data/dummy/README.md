# dummy_mail · 더미 메일 데이터

> 작성: 2026-10-17 · 버전 v1

## 1. 목적

메일 업무 누락 방지 시스템이 **업무 메일에서 메타데이터를 제대로 추출하는지** 평가하기 위한 더미 데이터.
메일 원문(입력)과 정답 라벨(기대 결과)을 한 쌍으로 만든다.

- 대상 기업: LG CNS (가상 조직도 기준)
- 메일함 주인: 클라우드전환1팀 이준호 팀장 (가상)
- 분량: 하루치 100건 (2026-10-19 수신, 스레드 시작 메일 2건만 10-16 수신)
- 근거: 팀장 기준 하루 100~200건 수신

## 2. 파일 구성

| 파일 | 역할 | 직접 수정 |
|---|---|---|
| `people.py` | 가상 조직도 25명, 배포 목록, 상급자, 즐겨찾기 | O |
| `mails.py` | 메일 100건 정의 (제목·본문·유형·정답 Task) | O |
| `build.py` | 인사말·서명란 조립, 우선순위 계산, 검증, 결과 파일 생성 | 규칙 변경 시만 |
| `dummy_mails.json` | 생성 결과 (평가에 쓰는 파일) | X (자동 생성) |
| `mail_list.md` | 100건 한 줄 요약 목록 | X (자동 생성) |

## 3. 사용 방법

```bash
cd data/dummy        # 레포 루트에서
python build.py
```

- 메일 추가·수정 → `mails.py` 수정 후 `build.py` 실행
- 사람 정보 수정 → `people.py` 수정 후 실행. 인사말·서명란이 전체 메일에 자동 반영됨
- 실행하면 분포·우선순위·태그·검증 오류를 출력함. **검증 오류 0**이어야 정상

## 4. 데이터 구조

메일 1건 = `mail`(입력) + `gold`(정답).

```json
{
  "mail": {
    "id": "M-0006", "thread_id": "T-0006", "received_at": "2026-10-19T08:47",
    "from": "yujin.choi@lgcns.example", "is_vip": true,
    "to": ["junho.lee@lgcns.example"], "cc": [],
    "subject": "...", "body": "인사말 + 본문 + 서명란", "attachments": []
  },
  "gold": {
    "sender": { "name": "최유진", "position": "선임", "team": "클라우드전환1팀" },
    "action_types": ["수정재전송요청"],
    "mentioned_me": true,
    "tasks": [{ "action": "...", "format": "pptx/drawio", "due_raw": null, "due_at": null }],
    "urgent": false, "is_follow_up": false, "priority": "P2", "tags": ["마감없음"]
  }
}
```

| 필드 | 의미 |
|---|---|
| `is_vip` | 발신자가 메일함 주인의 즐겨찾기에 있으면 true. 플랫폼 설정값이라 `mail`에 둠 |
| `action_types` | 행동 유형 다중 라벨. 첫 번째가 주 유형 |
| `mentioned_me` | 본문에서 메일함 주인을 지목했는지 (CC·공지 속 개인 요청 판별용) |
| `tasks[]` | 메일에서 생기는 할 일. 한 메일에 요청이 2개면 2개 |
| `due_raw` / `due_at` | 마감 원문 표현 / 해석한 시각 |
| `priority` | 중요도 규칙을 정답 필드에 적용한 기대 결과 |
| `tags` | 엣지케이스 표시 (평가 시 유형별 오답 분석용) |

**저장하지 않는 값:** TO/CC 여부, 마감 출처, 외부 발신 여부, 재요청 횟수는 다른 필드에서 계산 가능해서 뺐음. 확신도·처리 상태는 시스템이 만드는 값이라 정답 데이터에 넣지 않음.

## 5. 생성 규칙

**유형 분포 (요청 비중 60%)**

| 유형 | 건수 | 유형 | 건수 |
|---|---|---|---|
| 자료제출요청 | 16 | 회신 (내 요청에 대한 답) | 8 |
| 수정재전송요청 | 10 | 공지 (개인 지목 4건 포함) | 16 |
| 회신요청 | 14 | 참조 | 14 |
| 검토승인요청 | 8 | 기타 | 6 |
| 일정참석 | 8 | **합계** | **100** |

**중요도 규칙** (`build.py`의 `priority` 함수)

| 신호 | 점수 |
|---|---|
| 상급자(담당·사업단장) 또는 즐겨찾기 발신 | +30 (중복 가산 없음) |
| 가장 이른 마감까지 24시간 이내 / 72시간 이내 | +30 / +15 |
| 긴급 표현 (`urgent`) | +15 |
| 재요청 (`is_follow_up`) | +20 |
| TO 직접 수신 / CC 수신 | +10 / −10 |

P1 70점 이상, P2 40~69점, P3 40점 미만.

**마감 해석 기준 (임시)**
- 시각이 없는 마감 → 해당일 18:00
- '오전 중' → 12:00, '즉시' → 수신 후 약 1시간
- '다음 주 초' → 다음 주 화요일 18:00
- 일정참석 유형 → 응답 기한이 없으면 행사 시각

**개인정보 처리:** 인물은 모두 가상. 이메일 도메인은 `.example`, 전화번호는 `02-0000-xxxx`, 본사 주소는 `[본사 주소]` 자리표시자.

## 8. 알려진 문제와 다음 할 일

**규칙 쪽 (팀 결정 필요, 데이터는 그대로 둠)**
1. **P3 쏠림:** Task 메일 60건 중 31건이 P3. 팀장 메일함에서는 팀원 요청이 많은데 팀원 발신은 가산점이 없음
2. **사례 1이 P2로 하락:** 메일함 주인이 팀장이라 타팀장이 상급자가 아님
3. **회의 시간 변경이 P1 (M-0089):** 즐겨찾기 + 24시간 내 일정 + TO가 겹쳐 70점
4. 즐겨찾기와 상급자를 따로 가산할지 (최대 +60) 결정 필요

**데이터 쪽**
1. 스레드 추가: 7개 → 약 15개. 재요청·상대 대기 테스트용 답장 메일 보강
2. 마감 해석 기준(5절) 팀 확정 후 정답 라벨 재검토
3. 정답 라벨 내용 검수: 검증 스크립트는 형식·일관성만 확인하므로 `mail_list.md`로 사람이 확인
4. 팀원 메일함 세트 추가 (직급별 차이 검증)

## 9. 평가 (`eval.py`)

```powershell
python eval.py predictions.json   # -> eval_report_predictions.md
python eval.py --selfcheck        # 채점 로직 점검 (gold를 예측으로 넣으면 100%인지 등)
```

- 입력: `[{"id": "M-0001", ...gold와 같은 필드}]` 리스트. `tags`는 필요 없음. 빠진 메일·필드는 오답
- 메일 완전 정답 기준: 주 유형, Task 여부, Task 수, 마감, 지목, 긴급, 재요청, 우선순위 모두 일치
- 핵심 지표는 **Task 메일 재현율** (할 일 메일 누락 여부). 마감은 `due_at` 분 단위 일치
- Task는 메일 안에서 `action` 글자 유사도(difflib) 순으로 1:1 매칭. action 문장 유사도는 참고용
- 리포트: 핵심 지표 → 필드별 정확도 → 이진 판정 P/R/F1 → Task 추출 → 유형별 F1 → 우선순위 혼동 행렬 → 태그별 정답률 → 오답 목록
