## 1. 한 줄 정의와 IR 포지셔닝

### 1.1 한 줄 정의

여러 메일 계정의 미처리 업무를 모아 보여 주고, 사용자가 말로 지시하면 에이전트가 처리하며, **처리 완료 체크까지 추적하고 리마인드하는 웹 앱**

### 1.2 IR 포지셔닝 `[확정]`

> **"그룹웨어를 바꾸지 않고, 쓰던 메일 위에서, 처리 완료까지. 모든 것은 사내 모델로, 외부 유출 없이."**

| 메시지 | 근거 | 시연에서 보여 줄 장면 |
|---|---|---|
| 그룹웨어를 바꾸지 않음 | 두레이 · 네이버웍스 AI는 자기 메일함 안에서만 동작한다. 우리는 기존 Outlook 위에 붙는다 | Outlook 테스트 계정 그대로 연결 |
| 쓰던 메일 위에서 | 여러 계정의 미처리 메일을 한곳에 모은다 | 계정 2개 동시 표시 |
| 처리 완료까지 | 경쟁 서비스는 요약 · 우선순위에서 끝난다. 우리는 완료 체크까지 추적 · 리마인드한다 `[미확인: 경쟁사 추적 기능 부재]` | 리마인더 도착 → 처리 → 추적 종료 |
| 사내 모델, 외부 유출 없음 | 서비스 경로는 엑사원 자체 운영. 외부 LLM API 호출 0건 (D41) | 외부 송신 로그 0건 화면 `[제안]` |

### 1.3 기능 위계 `[확정]` (D42)

- 기본 기능: 요약, 초안. 있어야 하지만 차별점이 아니다. 시연은 짧게 한다.
- 시연 중심: **행동형 에이전트**. 말하면 상태가 바뀌고, 끝날 때까지 추적된다.

## 4. 처리 완료 추적 · 리마인더

### 4.1 상태 머신 `[확정]` (D36 · 구조도 v3.1 5절)

```
미처리 ──완료──▶ 완료 ──되돌리기──▶ 미처리
미처리 ──제외──▶ 제외 ──되돌리기──▶ 미처리
미처리 ──나중에(until)──▶ 나중에 ──until 도래──▶ 미처리 (리마인더 발송)
```

- 상태는 업무(`tasks`) 단위로 둔다. 한 메일에 업무가 여러 개일 수 있기 때문이다(D20-6). 코드 값은 `pending` · `done` · `excluded` · `snoozed`.
- 추적 종료 조건은 사용자의 **완료 체크** 또는 **제외**뿐이다. 회신을 보냈다고 자동 완료하지 않는다 `[확정]`. 서비스 안 답장 뒤에는 완료 확인 팝업(D23)을 띄운다.
- 모든 전이는 `action_log`에 기록한다(누가 · 언제 · 어디서: UI / 에이전트 규칙 / 에이전트 모델 / MCP).

### 4.2 리마인더 규칙 `[제안]` (기본값은 설정에서 바꾼다)

| 규칙 | 조건 | 기본값 |
|---|---|---|
| R-기한 | 기한이 있는 미처리 | 기한 전날 + 당일 오전 |
| R-경과 | 기한이 없는 미처리 | 수신 후 N일마다 `[결정 필요: N]` (권장 2일) |
| R-나중에 | 나중에 처리 시각 도래 | 해당 시각 |
| R-요약 | 사용자 설정 주기 | 매일 1회 (미처리 개수 요약) |

- 발송 직전 재확인: 아직 미처리인지 다시 조회한 뒤 보낸다. 완료 · 제외면 건너뛰고 사유를 남긴다.
- 중복 방지: `reminders`의 `(task_id, rule, slot)` 유일 제약. `slot`은 규칙별 발송 시각(예: `2026-11-06T09:00`).
- 조용한 시간: 설정 시간대에는 보류했다가 다음 허용 시각에 보낸다.
- 스케줄러는 **단일 프로세스**로 운영하고, 시작할 때 DB에서 예약을 다시 만든다 (R3).
- 데모용 시간 이동 · 리마인더 강제 실행 엔드포인트는 개발 모드(`APP_MODE=dev`)에서만 켠다.

### 4.3 알림 채널 `[결정 필요]`

- 권장: 앱 내 알림 센터 + 웹 푸시(PWA) 2개로 제한한다.
- 웹 푸시는 HTTPS가 필요하다 → 11/14 배포 URL과 함께 확보.
- iOS 웹 푸시는 홈 화면에 설치했을 때만 동작한다 → 설정 화면에 설치 안내 (R4).
- Apprise는 다른 채널(메일 · 메신저) 확장용으로 유지한다.

## 5. 응답 없는 메일 확인 (조치 없음, 확인만) `[확정 방향]`

- 대상: 보낸편지함에서 수집한 내 발신 메일(`mails.direction = sent`).
- 판정: 같은 대화(`conversation_id`)에 상대 회신이 **기준일(기본 3일)** 동안 없으면 '응답 대기' 목록에 표시한다.
- 제외: 자동 발송, 회신이 필요 없는 메일(공지성) `[결정 필요: 전체 발신 메일 vs 요청성 메일만]` (권장: 1단계는 전체 발신 메일에서 자동 발송만 제외, 기준 3일).
- 화면: '응답 대기' 목록 + 경과일. 자동 후속 발송 · 자동 초안은 없다.
- 사용자가 원하면 해당 메일에서 회신 초안(T07)이나 템플릿 전송(T14)으로 이어갈 수 있다.
- 구현 전제: 동기화가 보낸편지함도 가져오고, 사전 필터는 보낸 메일을 저장한 뒤 분류에서만 뺀다(구조도 v3.1 4절).

## 6. 캘린더 화면 `[확정 방향]` (P1)

- 앱 내 별도 화면. 월 · 주 보기.
- 표시 대상: 기한이 있는 미처리 업무, 나중에 처리 예정 업무.
- 날짜 클릭 → 해당 날짜 업무 목록, 업무 클릭 → 메일 미리보기.
- (P2) 드래그로 나중에 처리 날짜 변경.
- **Outlook 캘린더에 쓰기 연동은 하지 않는다** (범위 밖).

## 7. 템플릿 전송 (선택 기능, P2)

- 흐름: 메일 선택 → 템플릿 선택 → 수신자 · 제목 · 본문 미리보기 → **확인** → 발송 → 결과 표시.
- 템플릿: 이름, 제목, 본문(자리표시자 `{수신자명}` · `{원메일제목}` 등), 소유자. 기존 `templates` 테이블에 종류 `send`와 제목 칸을 더한다(구조도 v3.1 9절).
- 기본 템플릿 예: "확인했습니다", "검토 후 회신드리겠습니다", "일정 조율 부탁드립니다".
- 발송 후에도 해당 업무는 **자동 완료하지 않는다**. 완료 체크는 사용자가 한다 (D36).
- 필요 권한: 메일 발송 권한 추가 동의 (Graph `Mail.Send` `[미확인: 테스트 계정 정책]`). 권한이 없으면 기능을 숨긴다 (R6).
- 주의: PRD '메일 앱 자체 기능 만들지 않음'과 충돌 소지가 있다 → `[결정 필요]` 포함 여부와 PRD 문구 조정 (권장: P2 선택 기능으로 넣고, 문구는 "자동 발송 없음"으로).

## 10. 데이터 모델 변경

기준 문서는 구조도 v3.1 9절이다. 핸드오프 10절과 다른 점만 적는다.

| 핸드오프 제안 | 반영 | 이유 |
|---|---|---|
| `mails`에 `status` · `snooze_until` · `due_at` · `due_source` · `evidence_text` | `tasks`에 둔다 (`snoozed_until` · `due_source` · `evidence_text`) | 한 메일에 업무가 여러 개일 수 있다(D20-6) |
| `mails`에 `category` · `category_source` · `direction` · `conversation_id` | `mails`에 둔다. `conversation_id`는 v3 `thread_id`를 이름만 바꾼다 | 분류와 대화 묶음은 메일 단위다 |
| `mails.is_important` | `contacts.is_superior` · `is_favorite`로 대신한다 | 중요 여부는 발신자 기준(D9, T11) |
| `reminders` 유일 `(mail_id, rule, slot)` | `(task_id, rule, slot)` | 리마인더 대상은 업무다 |
| `action_log` 신규 | 신규. v3 `agent_logs`와 `tasks.done_by`를 대체한다. `before_json`(되돌리기용) 추가 | UI · 에이전트 · MCP 공용 기록 |
| — | `action_previews` · `notifications` · `push_subscriptions` 신규 | preview 1회 실행 보장 · 알림 센터 · 웹 푸시 |
| `templates` 신규 | 기존 `templates`에 종류 `send` · 제목 추가 | 이미 `reply` · `rule` 템플릿이 있다 |
| `settings` 리마인드 주기 · 조용한 시간 · 무응답 기준일 · 본문 토글 | 그대로 추가 | — |
| `favorite_senders` 기존 유지 | 해당 테이블 없음. `contacts.is_favorite`가 같은 역할 | 구조도 v3 8절 |

## 13. 벤치마킹 결론 (조사일 2026-11-02)

조사 내용(해외 · 국내 · LG 사내 도구)과 출처는 `refs/benchmark.md` 맨 위 스크랩 「행동형 에이전트 · 국내 그룹웨어 · LG 사내 도구 묶음 조사 (2026-11-02)」에 있다. 여기에는 결론만 둔다.

1. 요약 · 초안 · 일정은 국내외 모두 기본 기능 → 차별점이 아니다.
2. 업계 흐름은 2026년 상반기 '요약 · 초안' → '행동형 에이전트'로 이동했다. 가장 가까운 경쟁은 NHN 두레이 '마이 에이전트'다.
3. 우리 차별점: **처리 완료까지 추적 + 리마인드, 기존 메일 위에서, 사내 모델로**.
4. LG CNS 대상으로는 a:xink와 경쟁이 아니라 **보완**으로 포지셔닝한다 `[제안]` — "a:xink가 아침에 알려 준 일이 실제로 끝났는지, 완료 체크까지 추적하고 다시 알림".
5. LG CNS 에이전틱웍스가 MCP 방식으로 연동하므로 행동을 MCP로 노출하는 구조를 둔다 (D43, AI detail 5절).
6. 확인 필요: a:xink가 미처리 추적 · 리마인드를 하는지 `[미확인]` → `refs/interview.md` 2차 질문지 '사내 도구 1'.
