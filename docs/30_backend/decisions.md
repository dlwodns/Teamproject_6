## 1. 결정

### BE-D21 · 문맥 기억은 분류와 따로 모델을 부르고, 정해진 칸(맡은 일 · 소속)에만 넣는다 — 파이프는 지금 만들고 모델 연결 뒤 켠다 (2026-11-11)

- 상태: 채택(구현 완료 · 모델 연결 전) · 제안: 문규남 · 결정: 문규남(11-11, "만들어 놓고 나중에 연결하면 이것도 됩니다") · 리뷰: [미정] · 공동: — · 근거: BE-D17 · BE-D18 · AI-15(근거 문장) · AI-D15(분류 프롬프트 동결)
- 결정 1: ai에 `POST /memory/extract`를 둔다(프롬프트 memory_v1). 보낸 사람에 대해 `works_on` · `org`만 뽑고, 근거 문장이 본문에 글자 그대로 없으면 버린다.
- 결정 2: backend는 분류가 끝난 메일에 대해 `MEMORY_EXTRACT=1`일 때만 부른다(기본 꺼짐 — 엑사원을 연결해 실측한 뒤 켠다). 저장은 `contact_facts`, 기록 · 되돌리기 · 사용자 우선은 기억 변경과 같다.
- 결정 3: 읽는 곳은 제안 카드의 사람 표시와 '에이전트가 아는 것' 화면이다(BE-D18). 초안(T07 · T12)에 상대 맥락으로 넣는 것은 초안 경로가 backend에 생길 때 더한다.
- 확인(11-11): ai 시험 3개(근거 없는 사실 · 없는 종류 · 긴 값 버림, 모델 꺼짐 fallback), backend 시험 7개(스위치 · 흐름 · 사외 메일 · 실패 · 설정 · 사용자 수정 · 계약), 실제 ai 서비스(모델 꺼짐)에 `/memory/extract` 호출 → fallback 확인. 엑사원 실측은 D52 뒤.
- 발표 표현(D50 결정 7): "문맥 기억은 파이프와 시험까지 만들었고, 모델을 연결하면 동작한다"까지만 말한다. 실측 전에는 "구현했다"고 하지 않는다.

### BE-D20 · 템플릿의 '업무 분류 규칙'(kind = rule)을 뺀다 (2026-11-11)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-11) · 리뷰: [미정] · 공동: — · 근거: AI-D15(판단은 모델 · 규칙은 조건만) · BE-D18(읽는 곳이 없는 값은 두지 않음) · 와이어프레임 설정 › 템플릿
- 배경: `templates.kind = rule`은 와이어프레임의 '업무 분류 규칙(조건 → 성격)'이었다. 사용자가 "이런 메일은 이렇게 분류"를 정해 두는 기능인데, 칸만 있고 읽는 곳이 없었다.
- 결정: 구조도 9절 · 와이어프레임 설정 › 템플릿 · 기획 detail에서 뺀다. 테이블 제약은 `reply` · `send`만 받는다(새로 만드는 DB부터. 예전 DB의 rule 행은 읽는 곳이 없어 그대로 두어도 무해).
- 근거: AI가 이미 분류한다. 사용자 규칙이 AI 결과를 덮어쓰면 판단이 규칙으로 되돌아가고(AI-D15와 반대), 정답 세트로 잰 정확도가 서비스 품질을 대표하지 못한다. 설정에서 규칙을 짜는 사용자는 적고, 중요한 사람(T11 · 메일 기억하기) · 업무 아님(T10)과 겹친다.
- 남기는 것(P2): 같은 보낸 사람을 '업무 아님'으로 두세 번 빼면 에이전트가 "앞으로 이 주소는 계속 뺄까요?"라고 제안한다(사용자 교정이 다음에도 유지되게). 설정 화면에서 규칙을 짜게 하지 않는다. 정확도는 AI 결과와 사용자 교정 결과를 따로 센다.
- 알릴 곳: templates 테이블은 팀 공유다. BE-D16 공지와 함께 알린다.

### BE-D19 · 메일 분류는 대기열 작업자가 하고, 요청의 기억 칸은 돌 때 만든다 (2026-11-11)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-11, "ai 분류 쪽 이어서 연결") · 리뷰: [미정] · 공동: — · 근거: 구조도 4 · 12절 · BE-9(#28) · BE-D18 · AI-D15
- 결정 1: 메일 저장 경로는 `services/ingest.after_mail_saved` 하나만 부른다(메일 기억하기 + 분류 대기열). 작업자는 본문 가져오기 → 요청 만들기(`ai_client/payload.py`, 기억은 `memory.classify_context`) → `/classify` → 저장 순서로 한 통씩 한다.
- 결정 2: ~~실패(ai 꺼짐 · 제한 시간 · 형식 · 모델 실패 fallback · 본문 없음)는 3번까지 다시 시도하고 `failed`로 남긴다. 빈 본문이나 규칙만의 결과로 조용히 저장하지 않는다.~~ → **11-12 #44 리뷰(홍태겸)로 바꿈**:
  - ai 꺼짐 · 제한 시간은 실패로 세지 않고 `queued`로 남긴다(구조도 12절 #17). 작업자는 실패 뒤 INTERVAL만큼 쉰다. 처음 안은 꺼진 ai에 몇 ms 안에 3번 부르고 `failed`가 됐다.
  - 모델 실패 fallback도 규칙이 찾은 할 일 · 확인 칸을 저장한다(`source = rule`). ai는 fallback이어도 규칙 결과를 채워 보내므로, 버리면 엑사원 연결 전에는 모든 메일이 업무 0건으로 `failed`가 된다. 작업에 `fallback`을 남겨 엑사원 재분류 대상으로 표시하고, 다시 돌리면 사용자가 손대지 않은 규칙 결과만 바꾼다.
  - 형식 · 본문 없음 · 그 밖의 예외는 실패로 세서 3번이면 `failed`, `POST /api/classify/retry`로 되살린다. 어떤 예외도 `running`으로 남기지 않고, 오래된 `running`은 `started_at` 기준으로 되살린다. 화면에 센다(누락 0).
- 결정 3: 배포 목록에 종류(직책 · 팀 · 전사)를 둔다. AI-19 계약(owner.role_lists · team_lists)이 "직책 · 팀 목록으로 온 지시는 나에게 온 것"을 이 구분으로 판단하기 때문이다. 종류는 주소로 짐작하고 화면에서 고칠 수 있다.
- 결정 4: BE-9(#28)의 응답 형식을 지금 ai 계약에 맞춘다. `confidence`는 없어도 되고(AI-19부터 None), 업무에 `type` · `due_time_stated` · `end_at` · `deliver_to`를 받는다(저장 칸은 #30 정리 때).
- 의존: 이 작업은 #28(BE-9 ai_client) 위에 쌓인다. #28이 먼저 머지되어야 한다.
- 확인: 실제 ai 서비스(모델 꺼짐)에 붙여 `/classify` 200 · 계약대로 읽힘을 11-11 확인(그때는 fallback을 다시 시도로 보냈다. 11-12부터 규칙 결과 저장). 엑사원을 켠 실측은 ai 호출부 교체(D52) 뒤.

### BE-D18 · '에이전트가 아는 것'은 읽는 곳이 정해진 구조화된 값만 두고, 메일 분류로 가는 입구는 하나다 (2026-11-11)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-11, "비용 말고 바람직하고 우수한 구조") · 리뷰: [미정] · 공동: — · 근거: AI detail 2절 T11 · 구조도 9절 contacts · AI-D15 · D50 결정 7
- 배경: 첫 구현은 '늘 지키는 규칙'을 자유 문장(`templates.kind = rule`)으로 저장하고 "판단할 때 지켜요"라고 보여 줬지만, 그 값을 읽는 곳이 없었다(분류 요청에 칸이 없고 backend 규칙도 읽지 않음). T11의 계약은 처음부터 자유 문장이 아니라 연락처 표시(`level` = superior · favorite)였다.
- 결정 1: 기억은 읽는 곳이 정해진 구조화된 값만이다(내 직책 · 팀 · 배포 목록, 상급자, 즐겨찾기). 화면은 항목마다 읽는 곳(`used_by`)을 보여 준다. 읽는 곳이 없는 값은 기억으로 보여 주지 않는다.
- 결정 2: 자유 문장 규칙 API(`/api/agent/memory/rules`)를 없앤다. T11은 `memory.apply_t11()`로 연락처 표시를 켠다.
- 결정 3: 메일 분류 요청의 owner · sender 칸은 `memory.classify_context()` 한 곳에서 만든다. ai 호출부(BE-9)는 이것만 쓴다. 기억이 바뀌면 다음 분류부터 들어간다.
- 근거: 자유 문장 규칙을 모델에 넘기면 판단이 흔들리고(동결 프롬프트 · 측정 무효), 메일 속 문장처럼 검증할 수 없는 지시가 된다. 구조화된 값은 규칙 · 모델 · 화면이 같은 값을 읽고, 되돌리기 · 기록 · 시험이 가능하다.
- 남은 일: `templates.kind = rule`은 읽는 곳이 없다. 구조도 9절에서 뺄지 팀이 정한다 `[결정 필요]`. ai 호출부(BE-9)가 `classify_context()`를 쓰게 연결한다.

### BE-D16 · 모든 backend 경로가 요청한 사용자를 확인하고, 쓰기 본문은 엄격하게 받는다 (2026-11-11)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-11) · 리뷰: [미정] · 공동: — · 근거: D50 · PL-16 · `agent_api_contract.md` 2절 · 11-11 리뷰(다른 사용자의 업무 · 기억을 바꾸고 되돌릴 수 있었음)
- 결정 1(사용자): BE-4 업무 경로(`PATCH /api/tasks/{id}` · `POST /api/tasks/bulk/preview` · `POST /api/actions/execute` · `POST /api/actions/{id}/undo`)를 포함한 모든 경로가 `X-User-Id` 헤더로 사용자를 정한다. 헤더가 없으면 개발 모드에서만 1번 사용자, 운영 모드는 401. 그 사용자가 DB에 없으면 401. 남의 업무 · 기록 · 미리보기를 가리키면 404. 판정은 `app/core/user.py` 한 곳이고, 로그인을 붙일 때 그 함수만 바꾼다.
- 결정 2(엄격한 입력): 업무 상태 변경 본문에 모르는 칸이 오면 422(`vai` 같은 오타가 조용히 빠지지 않게). `execute`는 `preview_id` 말고 받지 않는다(확인 뒤 대상 바꿔치기 금지). `snoozed_until`은 날짜와 시각이 함께 있는 ISO 문자열만 받는다(숫자 epoch · 날짜만은 422). 경로 id는 1 ~ 2^63-1, 넘으면 422(500이 아니라).
- 결정 3(응답 시각): 응답 시각은 초까지만 낸다(`YYYY-MM-DDTHH:MM:SS+09:00`).
- 결정 4(제안 카드 숨김): 다음 R-아침까지 숨기되, 1시간도 안 남았으면 그다음 날 R-아침까지 숨긴다(문규남 11-11 채택).
- 영향: 프런트엔드는 개발 모드에서는 지금처럼 헤더 없이 써도 된다. 운영 모드 배포(INF) 전에 모든 요청에 `X-User-Id`를 붙인다. 업무 상태 변경에 정의되지 않은 칸을 보내던 곳이 있으면 422가 난다.
- 대안: 사용자 확인 없이 두고 로그인 때 한꺼번에 막기 — 기억(상급자 표시 · 규칙)까지 남이 되돌릴 수 있게 되어 기각.

### BE-D15 · 시각은 시간대 없는 한국 시간(naive KST)으로 저장하고 ai에 보낸다 (2026-11-04)

- 상태: 제안 · 제안: 홍태겸 · 결정: [파트 팀장] · 리뷰: [미정] · 공동: — · 근거: BE-1(#7) · #4 리뷰
- 결정: `app/core/clock.now()`는 시간대 없는 한국 시간을 낸다. DB의 모든 시각과 ai에 보내는 `received_at` · `now`도 같은 형식이다.
- 근거: SQLite DateTime은 시간대를 저장하지 않아 읽으면 naive로 돌아온다. 시간대 있는 `now()`와 섞어 비교하면 TypeError가 난다(BE-1에서 재현). ai 서비스(#4)도 naive 시각을 전제로 해서 시간대 있는 값을 보내면 500이 날 수 있다.
- 대안: 모두 시간대 있는 값(aware)으로 통일 — SQLite 칸 처리와 ai 코드 수정이 함께 필요해 기각. UTC로 저장 — 기한 18:00 · 리마인드 08:30이 한국 시간 기준이라 변환 실수 위험이 커서 기각.
- 위험 · 남은 일: 서버 밖(Outlook Graph)에서 받는 시각은 시간대가 붙어 오므로 저장 전에 KST로 바꾸고 시간대를 뗀다(BE-7). #4 리뷰의 시간대 질문은 D47로 확정됐고 이 결정과 같다(ai 응답은 naive KST, backend → frontend 응답에는 `+09:00`).

### BE-D17 · 시연 시각 CLOCK_START: 서버 시작 때 offset을 정하고, 시각은 실제 시간만큼 흐른다 (2026-11-12)

- 상태: 결정 · 제안: 임동하 · 결정: 임동하(BE 파트 팀장) · 리뷰: [미정] · 공동: — · 근거: BE-D15 · BE-14 · `feature/BE-clock-start`
- 결정: 서버 시작 때(lifespan, 설정 검사 뒤) `offset = CLOCK_START - 실제 현재 KST`를 한 번 계산하고, `clock.now()`는 `실제 현재 KST + offset`을 낸다. 멈춘 시각이 아니라 실제 시간만큼 계속 흐른다. 실제 시각은 UTC로 받아 KST로 바꿔 서버 OS 시간대에 기대지 않는다. 시간대 없는 입력은 KST로 보고, 시간대 있는 입력(`+09:00` · `Z` 등)은 KST로 바꾼 뒤 시간대를 뗀다(BE-D15 naive KST). 비어 있으면 offset 0(실제 시각), 틀린 값이면 설정 검사(`check_settings`)에서 서버 시작을 막는다. 시간 이동(BE-14)용 `clock.set_offset(timedelta)`은 기존 offset을 **교체**한다(누적하지 않는다). offset 계산은 offset이 들어간 `now()`가 아니라 `real_now()`로 해 다시 초기화해도 누적되지 않는다.
- 근거: 시연 시나리오(기한 18:00 · 리마인드 08:30)를 정해진 날짜에서 시작해 실제 시간 흐름 그대로 보여야 한다. 시각을 `clock` 한 곳에서만 얻으므로(BE-D15) offset 하나로 서비스 전체 시각이 같이 움직인다.
- 대안: 고정 시각(멈춘 시계) — 시간이 흐르지 않아 리마인더 · 기한 지남을 보여줄 수 없어 기각. offset을 DB · 파일에 저장 — 다중 worker 공유 · 재시작 유지가 되지만 이번 시연 범위에 비해 커서 보류. `set_offset`을 더하기 함수로 — 반복 호출 시 누적 실수 위험이 있어 교체로 정함(더하려면 `get_offset() + Δ`를 넘긴다).
- 위험 · 남은 일: offset은 프로세스별 메모리 상태다. 재시작(`--reload` 포함)하면 `CLOCK_START` 시각부터 다시 시작하고, worker가 여럿이면 서로 다른 offset을 가진다 → BE-14 시간 이동은 단일 worker를 전제로 한다(공유 · 영속화는 범위 밖). 시간 이동 · 리마인더 강제 실행 라우터는 `APP_MODE`와 관계없이 `DEMO_TOOLS=true`일 때만 등록하고(`APP_MODE=dev`여도 false면 등록하지 않음), prod 시연 서버에서는 프록시 기본 인증으로 막기로 확정했다 — 라우터 · `DEMO_TOOLS` · 인증은 BE-14 · 인프라 후속 구현이며 이 결정에서 만든 것이 아니다. 아직 "dev에서만"으로 남은 곳: 공통 문서 `docs/00_common/architecture.md` 342 · 364줄, `docs/10_planning/detail.md` 124 · 235줄(문규남이 맞춘다), 코드 · 설정 주석 `backend/app/core/config.py` 13줄, `.env.example` 28줄(BE-14 작업 때 맞춘다). 번호: #47이 BE-D16, #44가 BE-D16~D21을 쓰고 있어 병합 전에 번호를 다시 확인한다(먼저 main에 들어간 번호를 유지하고, 나중 PR이 다음 빈 번호로 바꾸며 참조 문서도 함께 고친다).
