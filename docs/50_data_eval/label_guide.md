# 라벨 가이드 (더미 메일 · 정답 작성용)

> 갱신: 2026-11-04 · 작성: 최수호 · 근거: DE-1(`plan.md` 8절) · DE-D9 · DE-D10 · DE-D12
> 쓰는 곳: 개발셋 v2(`dev4`)와 봉인 테스트 A · B를 쓰는 작성자(사람 · Claude). 작성자에게는 이 문서, `plan.md` 11절(메일 작성 가이드), 8.2절(구성표)만 준다. **테스트 작성자에게는 AI 규칙(`ai/`) · 프롬프트 · 개발셋 · 기존 테스트셋을 주지 않는다.**
> 기존 규약(`data/dummy/README.md` 4~6절, 기존 세트 파일 머리말)을 한곳에 모으고, 헷갈리는 메일 판정 기준을 더했다. 규약이 바뀌면 이 문서를 먼저 고친다. AI 규칙 파일은 보지 않고 썼다.

## 1. 정답의 기준

한 가지 질문으로 정한다: **메일함 주인 이준호 팀장이 이 메일 때문에 해야 할 일이 있는가, 무엇을, 언제까지.**

- 할 일 = 이준호가 무언가를 **만들거나 · 보내거나 · 결정하거나 · 참석**해야 하는 것. 회신 · 자료 제출 · 수정본 재전송 · 검토 의견 · 결재 승인 · 회의 참석이 여기에 든다.
- 할 일 아님 = 읽고 알고만 있으면 되는 것. 단순 공유 · 다수 대상 일반 안내 · 참조 · 결과 보고 · 내 요청에 대한 답.
- 판정이 갈릴 만하면 한쪽으로 정하고 `애매` 태그를 붙인다. 채점 보고서에서 따로 센다.

## 2. 9유형

| 코드 | 유형 | 할 일 | 붙이는 경우 |
|---|---|---|---|
| 자제 | 자료제출요청 | 있음 | 자료 · 문서 · 수치를 만들어 보내 달라 |
| 수정 | 수정재전송요청 | 있음 | 이미 보낸 것을 고치거나 다른 형식으로 다시 보내 달라 |
| 회요 | 회신요청 | 있음 | 의견 · 답 · 확인 결과 · 가부를 회신해 달라 |
| 검승 | 검토승인요청 | 있음 | 문서를 검토하거나 결재 · 승인해 달라 |
| 일정 | 일정참석 | 있음 | 회의 · 행사에 참석(또는 참석 여부 회신) |
| 회신 | 회신 | 없음 | 내가 보낸 요청에 대한 상대의 답 · 결과물 · 완료 알림 |
| 공지 | 공지 | 없음(개인 · 역할 지목이 있으면 있음) | 다수 대상 안내 · 당부 |
| 참조 | 참조 | 없음 | 다른 사람에게 보낸 메일의 참조 · 정보 공유 |
| 기타 | 기타 | 없음 | 사내 소식 · 뉴스레터 · 외부 행사 홍보 · 자동회신 · 시스템 알림 |

- 유형은 여러 개를 붙일 수 있고 **첫 번째가 주 유형**이다. 공지 안에 나에게 맡긴 일이 있으면 `"공지 자제"`처럼 공지를 앞에, 맡긴 일의 유형을 뒤에 쓴다.
- `build.py` 검증: 주 유형이 할 일 있음 5유형이면 `tasks`가 있어야 하고, 회신 · 참조 · 기타면 없어야 한다. 주 유형이 공지인데 `tasks`가 있으면 `men=True`여야 한다. 보낸 메일은 6절.
- 백엔드는 9유형을 5분류(D39)로 묶어 저장한다: 자제 · 수정 · 일정 → 요청, 회요 → 회신, 검승 → 검토, 공지 → 공지, 회신 · 참조 · 기타 → 기타. **유형 이름을 바꾸지 않는다.**

## 3. 칸별 규칙

할 일 하나는 4칸이다(업무 정의, DE-D21): **무엇**(9유형 + 할 일 문장 · 형식) · **언제까지**(마감) · **누구에게서**(발신자) · **누구에게**(보낼 곳). 종류는 9유형으로 고정하고 업무 주제는 따로 적지 않는다.

| 칸 | 규칙 |
|---|---|
| `tasks` | 할 일 하나 = `(할 일, 형식, 마감 원문, "MM-DD HH:MM"[, 보낼 곳])`. 요청이 두 개면 두 개. 할 일 문장은 무엇을 · 어떻게가 보이게 짧게(예: "팀 주간보고를 양식에 작성해 회신") |
| 형식 | 결과물 파일 형식(`xlsx` · `pptx` · `docx` · `pdf` · `drawio`, 둘 이상이면 `pptx/drawio`). 없으면 `None` |
| 마감 | 원문 표현과 해석한 시각을 짝으로 적는다(4절). 마감이 없으면 둘 다 `None` |
| 보낼 곳 (새 세트만) | 결과를 보낼 사람 · 장소. 비워 두면 요청자(발신자)다. 본문이 다른 사람을 가리키면 그 사람 키(`"ysy"`), 배포 목록이면 `"@t1"`, 공유 폴더 · 포털처럼 장소면 짧은 글(`"PMO 공유 폴더"`). 공지 속 지목 요청은 본문에 제출처가 있으면 그쪽(예: 'PMO에 제출' → `"PMO"`). 나 자신은 안 된다. 개발셋 v2 · 테스트 A · B(`dev4` · `testA` · `testB`)에서만 정답에 들어간다(DE-D21) |
| `men` (지목) | 비워 두면 '할 일이 있고 내가 TO'일 때 True. CC로 받았는데 본문에서 나를 부르거나, 공지 안에서 나 · 우리 팀 · '각 팀장' 같은 역할로 일을 맡기면 `men=True`로 적는다. 지목은 일을 맡길 때만이다 — 할 일이 없는 메일은 이름이 불려도 비워 둔다(11/5) |
| `urgent` | '긴급' · '급히' · 'ASAP' · '즉시'처럼 서두르라는 표현이 있으면 True |
| `fu` (재요청) | 같은 요청을 다시 보낸 메일이면 True. 앞 메일과 같은 스레드(`th`)로 묶는다 |
| `th` (스레드) | 같은 대화의 메일(원 메일 · RE: · FW:)은 같은 값. 혼자인 메일은 비운다 |
| `raw` | 인사말 · 서명란 없이 본문만 쓰는 메일(뉴스레터 · 시스템 알림 · 자동회신)은 True |
| `priority` · `is_vip` | 쓰지 않는다. `build.py`가 중요도 규칙(`README.md` 5절)과 즐겨찾기로 계산한다 |
| `tags` | 5절 목록에서 고른다 |

## 4. 마감 해석

상대 표현은 **메일을 받은 날** 기준으로 푼다. 마감이 수신 시각보다 이르면 안 된다(`build.py` 검증). 주말 · 공휴일은 옮기지 않는다.

| 원문 | 해석 | 출처 |
|---|---|---|
| 시각 없는 날짜 · 요일("10/23까지", "수요일까지") | 그날 18:00 | README 5절 |
| 오전 중 · 오전까지 · 점심 전 | 그날 12:00 | README 5절 · 기존 세트 |
| 오늘 중 · 금일 중 · 퇴근 전 · EOD | 수신일 18:00 | 기존 세트 |
| 내일 · 익일 | 다음 날 18:00(오전이면 12:00, 시각이 있으면 그 시각) | 기존 세트 |
| 모레 | 이틀 뒤 18:00 | 기존 세트 |
| 즉시 · 바로 · 최대한 빨리 · ASAP | `due_raw`는 "ASAP", `due_at`은 비운다(시각을 지어내지 않음) | 11/5 사용자 결정(AI-18) · README 5절 |
| 금주 중 · 이번 주 내 · 이번 주 중으로 | 그 주 금요일 18:00 | 기존 세트 |
| 다음 주 초 · 차주 초 | 다음 주 화요일 18:00 | README 5절 |
| 차주 ○요일 · 다음 주 ○요일 | 다음 주 그 요일 18:00(오전이면 12:00) | 기존 세트 |
| ○○ 전까지 · ○○ 전에(회의 · 미팅 · 보고 전) | 메일에 그 일정 시각이 있으면 그 시각. 시각을 모르면 `due_raw`만 적고 `due_at`은 `None` | 11/5 사용자 결정(AI-18) |
| 일정참석 | 응답 기한이 없으면 행사 시작 시각 | README 5절 |
| "편하실 때" · "시간 되실 때" · 기한 언급 없음 | 마감 없음, 태그 `마감없음` | README 6절 |

- **마감은 '까지 · 전에 · 중 · 내로 · 이내'처럼 마감을 뜻하는 말이 붙은 날짜만이다(11/5 사용자 결정, AI-18).** 일정 안내 날짜 · 이미 지난 일 · 참고로 적은 날짜는 할 일 마감이 아니다. 예외는 일정참석으로, 응답 기한이 없으면 행사 시작 시각을 마감으로 둔다(위 표).

## 6. 보낸 메일 (DE-2 · DE-D10)

- 발신자는 메일함 주인(`frm="me"`), 받는 사람은 상대다. 태그 `보낸메일`을 붙인다.
- 번호: `build.py`는 받은 메일에 M-번호, 보낸 메일에 S-번호를 따로 매긴다. 보낸 메일을 더해도 받은 메일 번호와 스레드 번호는 바뀌지 않는다. 시연용 보낸 메일(DE-2)은 `mails_sent.py` → `python build.py demo`(plan 12절).
- 유형: 내가 상대에게 요청하면 그 요청 유형(자제 · 수정 · 회요 · 검승 · 일정). 요청이 없으면 답장은 회신, 여러 사람(팀 전체 등)에게 하는 안내는 공지, 일부에게 하는 공유 · 보고는 참조, 그 밖은 기타. 제목의 `[공유]` 말머리만 보고 정하지 않는다(#14 검수 11/5: S-0006 팀 일정 안내 → 공지).
- `tasks`는 비운다(내 요청은 상대의 할 일이다). `build.py`는 보낸 메일에 요청 유형 + 빈 `tasks`를 허용하고, 유형 분포 · 할 일 통계에서는 뺀다.
- 응답 대기(무응답) 대상은 **요청한 보낸 메일만**이다. 같은 스레드(`th`)에 상대 회신 메일을 넣으면 '회신 옴', 넣지 않으면 '회신 없음'이 된다. 기준 시각에서 3일이 지났는지는 백엔드가 계산한다.
- #10 시드는 `from`이 메일함 주인이면 보낸 메일로, `thread_id`를 대화 id로 읽는다. 백엔드에는 보낸 메일 중 5분류가 요청 · 회신 · 검토인 메일만 응답 대기로 세 달라고 요청했다(11/4). 경계 규칙(자동회신 · 재요청 · 일부 회신 · 72시간)은 기획 detail 5절(#17)을 따른다(임동하 · 이재운 확인 11/5).

## 7. 파일 형식

세트 하나 = 메일 정의 파일 하나(`mails_<세트>.py`). `build.py`가 인사말 · 서명란 · 중요도를 붙여 JSON과 한 줄 목록을 만든다.

```python
# -*- coding: utf-8 -*-
# <세트> 메일 정의. 작성자 · 작성일 · 수신일 · 무엇을 보지 않았는지 적는다.
from people import X

MAILS = []
EXTRA = {  # 세트에서만 쓰는 외부 인물. 도메인은 .example, 전화는 02-0000-xxxx
    "abc": X("이름", "직급", "회사", "부서", "name@company.example", "02-0000-7001"),
}
TARGET = {"자료제출요청": 0, "수정재전송요청": 0, "회신요청": 0, "검토승인요청": 0, "일정참석": 0,
          "회신": 0, "공지": 0, "참조": 0, "기타": 0}  # 받은 메일의 주 유형 개수(보낸 메일 제외)


def m(t, frm, subj, body, types, tasks=(), att=(), to=None, cc=(), urgent=False, fu=False,
      tags=(), th=None, men=None, day="10-22", raw=False):
    MAILS.append(dict(t=t, frm=frm, subj=subj, body=body, types=types, tasks=list(tasks), att=list(att),
                      to=list(to or ["me"]), cc=list(cc), urgent=urgent, fu=fu, tags=list(tags),
                      th=th, men=men, day=day, raw=raw))


# 받은 메일 예
m("0910", "abc", "[요청] 자료 요청", "본문(인사말 · 서명란은 build.py가 붙인다)", "자제",
  [("할 일 문장", "xlsx", "내일 오전까지", "10-23 12:00")], tags=["상대날짜"])
# 보낼 곳이 요청자가 아니면 다섯째 칸(새 세트만, 3절 · DE-D21)
m("0930", "abc", "[요청] 점검표 업로드", "본문", "자제",
  [("점검표를 PMO 공유 폴더에 업로드", "xlsx", "금요일까지", "10-23 18:00", "PMO 공유 폴더")])
# 보낸 메일 예(6절)
```

## 8. CI에 걸리지 않게

팀 CI(`scripts/check_boundaries.py --all` · `ruff` · 채점기 selfcheck)가 모든 파일을 검사한다.

- IP 주소 모양 글자(예: 숫자 넷을 점으로 이은 것)를 쓰지 않는다. "개발계 DB 서버"처럼 말로 쓴다.
- 실제 계정 홈 경로(드라이브 문자 + 사용자 폴더 경로 등)를 쓰지 않는다.
- 메일 주소는 `.example` 도메인만 쓴다. 전화번호는 `02-0000-xxxx`, 본사 주소는 `[본사 주소]`.
- 실제 회사 · 실명 · MailEx 원문 문장을 쓰지 않는다(D24). MailEx 원본은 `data/raw/`에도 올리지 않는다.
- 메일 정의 파일은 파이썬 문법 오류가 없어야 한다(`ruff`).
