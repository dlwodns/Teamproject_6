## DE-D10 · 보낸 메일에도 정답을 붙이고, 무응답은 요청한 메일만 본다 (2026-11-04)

- 위험 · 남은 일: 보낸 메일이 요청인지 판정하는 방법이 정해지지 않았다(규칙 / 엑사원, AI-17 회신 필요 여부 판별은 지금 P2). 11/7 시연은 더미 정답으로 판정하므로, 보낸 메일 정답에는 요청 여부가 드러나게 9유형(회신요청 · 자료제출요청 · 검토승인요청 등)을 붙인다. 더미 형식은 #10(BE-2 시드) 기준을 따른다: `thread_id` 유지(시드가 `conversation_id`로 넣음), `from`이 메일함 주인이면 보낸 메일, 보낸 시각은 `received_at`, `gold.action_types` 필수 · `tasks`는 비움, 기존 메일 ID는 그대로(임동하 확인 중). 기획 detail · PRD · 구조도 반영은 별도 PR(`docs/DE-2-no-reply-scope`).

- 위험 · 남은 일: 서비스는 여전히 엑사원이다(D41). 오픈라우터 점수는 '같은 규칙 · 프롬프트에서 모델별 성능'이고 서비스 성능 그대로가 아니다 — 보고서 머리와 `scores.md`에 모델 ID를 꼭 적는다. 모델 ID는 날짜가 붙지 않은 이름이라 제공자가 내용을 바꾸면 점수가 달라질 수 있다 — 보고서 머리의 모델 ID와 잰 날짜를 함께 본다(같은 계열의 날짜 고정판 `deepseek/deepseek-v4.1-flash-1017`도 있다, 11/7 목록). 두 모델 모두 가격이 낮은 쪽이라(입력 100만 토큰당 약 $0.05~0.10) 개발 세트를 자주 다시 재도 부담이 적다. 봉인 세트도 외부 제공자로 나가므로(가상 메일이라 개인정보는 없음) 오픈라우터 설정에서 학습 · 저장을 끈다. 비용은 보고서 '사용량 · 비용' 줄로 본다. 봉인 테스트는 모델 2종을 같은 날 한 번씩만 잰다(DE-D14).
- 추가(11/13, 엑사원 API): 서비스 모델이 엑사원 API로 바뀌어(D51 · D52) 엑사원도 같은 세트로 잰다. 서비스 동작 그대로 재는 실행은 `LLM_BACKEND=exaone_api` + `run_dummy.py --llm`(서비스 호출부, AI-22 #64)이고 결과는 `predictions_<세트>_api-k-exaone_v2.5.json`이다. `--model exaone:k-exaone_v2.5`(#46)는 추론 강도 등을 바꿔 보는 비교 실험용으로만 쓴다. 하루 한도에 걸리면 받은 결과를 남기고 멈추고, 같은 명령에 `--resume`으로 잇는다. 키는 `.env`의 `EXAONE_API_KEY`다. 가상 데이터만 보내므로 이용 약관 문제는 D53으로 정리됐다. 키는 30일 뒤 만료되고, 봉인 테스트를 재는 키는 학습 활용 동의를 끈 채로 둔다(켜면 하루 한도는 늘지만 보낸 메일이 학습에 쓰일 수 있다). 하루 호출 한도는 100회다(docs.exaone.ai FAQ, AI-22) — 메일 1통에 1회라 봉인 테스트 A(80통)와 dev4(40통)도 하루에 다 재지 못한다. AI 파트 키는 에이전트 개발에 쓰므로(11/13) 분류 측정(core50 · dev4 · 봉인 테스트 A)은 데이터 · 평가가 팀원에게 받은 키를 나눠 써서 잰다(11/14). 키를 바꿀 때는 `.env`의 `EXAONE_API_KEY`만 바꾸고 같은 명령에 `--resume`으로 잇는다(받은 출력은 키와 상관없이 이어진다). 봉인 테스트를 재는 키는 모두 학습 활용 동의를 끈 채로 둔다. AI-D19(#67)부터 모델이 판단하지 못한 메일은 규칙으로 메우지 않고 '분류 실패'(오답)로 채점한다. 그래서 '규칙만' 기준선은 더 재지 않는다(`scores.md`의 규칙만 줄은 옛 기록). 11/12 dev4 기준선은 이 전의 임시 실행기(`--exaone`, 레포에 올리지 않음)와 옛 파이프라인으로 쟀다(`scores.md` 8절 표 4).
- 추가(11/15, 추론 강도): 엑사원 측정은 서비스 기본값(`EXAONE_REASONING_EFFORT` 비움 = max)으로 한다(최수호 결정). 같은 날 dev4 · dev9를 max와 low로 재 보니 판단이 사실상 같았고(dev4 같은 5통 · 같은 칸, dev9 놓침 · 잡음 같음), low는 추론 토큰이 약 15% 적을 뿐 시간은 서버 혼잡에 더 좌우됐다(`scores.md` 9절). 봉인 테스트 A도 max로 잰다. 서비스 강도가 바뀌면 그 값으로 다시 잰다. 강도가 기본이 아니면 결과 이름에 `@low`처럼 붙어 서로 덮어쓰지 않는다(#64). 키를 바꿔 `--resume`할 때는 강도 환경 변수를 그대로 둔다 — 바꾸면 다른 결과 파일로 처음부터 다시 돈다.

## DE-D25 · 수정안은 여러 모델 · 여러 세트에서 반복된 것만 낸다 — 과적합 막기 (2026-11-07)

- 상태: 채택 · 제안: 문규남(11/7 회의) · 결정: 최수호 · 리뷰: [미정] · 공동: 문규남(AI) · 근거: D46 · DE-D7 · DE-9 · DE-D24
- 결정:
  1. 오픈라우터 2종 결과를 메일마다 맞댄다(`eval/runners/compare_models.py`). 둘 다 틀림 → 정답부터 확인한 뒤 규칙 · 프롬프트 후보. 하나만 틀림 → 그 모델 약점으로 기록하고, 다른 메일 · 세트에서도 반복되면 후보로 올린다(서비스는 더 작은 엑사원이라 큰 모델 하나가 틀린 것도 가볍게 넘기지 않는다).
     11/8(#38 리뷰): '틀림'은 **원출력**(합치기 전 모델 출력)으로 먼저 본다. 원출력이 모두 틀림 → 프롬프트 후보, 원출력은 맞는데 최종이 틀림 → 합치기 · 규칙 후보, 원출력은 틀렸는데 최종이 맞음 → 규칙이 받쳐 주는 메일(규칙을 덜면 드러날 수 있어 기록). 최종만 맞대면 규칙이 덮어쓴 것을 프롬프트 문제로 잘못 읽는다(`error_analysis.md` 7.5).
  2. 두 모델이 모두 정답과 다르면 정답(라벨)을 먼저 다시 본다. 라벨 가이드로도 갈리면 `애매` 태그를 붙이거나 가이드 문장을 분명히 고친다.
  3. 메일 한 통의 표현에 맞춘 규칙은 내지 않는다. 2개 이상 세트(또는 여러 메일)에서 반복되는 모양만 원리 문장으로 낸다. 고칠 수 있으면 단어 규칙보다 프롬프트의 판단 기준을 먼저 본다.
  4. 고친 뒤에는 고칠 때 본 세트와 보지 않은 세트(예: dev4 · dev7 · dev8)를 함께 다시 재고 `scores.md`에 나눠 적는다. 보지 않은 세트가 나빠지면 그 수정은 되돌리자고 제안한다. 최종 판단은 봉인 테스트(버전마다 1회, 오답 메일은 보지 않음)로 한다.
- 근거: 개발 세트에만 맞춘 규칙은 처음 보는 메일에서 틀린다는 AI 파트 의견(11/7 회의). 이미 차이가 보인다 — 개발 세트 7개는 규칙만 놓침 0 · 할 일로 잡음 0인데, 처음 본 테스트 A(v1.8)는 놓침 5 · 잡음 11, 새로 쓴 dev4는 놓침 2 · 잡음 1(`scores.md` 4 · 7절).
- 대안: 개발 세트 오답마다 규칙을 더한다 — 개발 점수는 오르지만 처음 보는 메일에서 틀린다.
  5. 누락 방지가 1순위다(D15). 놓침(할 일 메일을 놓침)은 한 번만 나와도 AI 파트에 '관찰'로 알리고, 비슷한 상황의 새 메일을 개발 세트에 보태 반복되는지 빨리 본다(규칙 · 프롬프트는 반복이 확인된 뒤). 할 일을 줄이는 수정안(잘못 잡음 줄이기)은 본문에 '할 일 없음'이 분명히 적힌 경우로 좁히고, 반영 뒤 모든 세트에서 놓침이 늘지 않았는지 먼저 확인한다(11/7 추가).
- 위험 · 남은 일: '반복'의 기준(몇 세트 · 몇 통)은 DE-9 2회차 결과를 보고 다시 정한다.

## DE-D26 · 라벨 기준 보강: 자료제출 ↔ 회신요청 · 사내 행사는 기타 · 서명은 보류 (2026-11-07)

- 상태: 채택 · 제안: 최수호(DE-9 2회차) · 결정: 최수호(누락 방지 1순위로 판단, D15) · 리뷰: [미정] · 공동: 문규남(AI, dev7 · dev8 작성 세트) · 근거: DE-D22 · DE-D25 · `error_analysis.md` 7.2절
