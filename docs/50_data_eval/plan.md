### 8.2 유형 구성

| 구분 | 개발셋 v2 (100) | 테스트 A · B (각 80) |
|---|---|---|
| 할 일 메일 | 50 — 자료제출요청 · 수정재전송요청 · 회신요청 · 검토승인요청 · 일정참석을 고르게 | 40 — 같은 5유형을 고르게(유형마다 6~10통) |
| 할 일 없는 메일 | 50 — 공지 · 참조 · 회신(내 요청에 대한 답) · 기타 | 40 — 같은 4유형(유형마다 8~12통) |
| 그중 헷갈리는 할 일 없는 메일 | 30통 이상(11절 목록) | 20통 이상 |
| 그중 어려운 할 일 메일 | 15통 이상(완곡 요청 · CC 지목 · 공지 속 개인 요청 · 마감 없음 · 상대 날짜 · 요청 2개 · 재요청) | 15통 이상 |

- 할 일 40통을 모두 찾으면 쓸데없는 할 일 2통까지가 정밀도 95% 이상이다(40/42 = 95.2%).
- 엣지케이스는 `tags`로 표시한다. 태그 목록은 라벨 가이드(`label_guide.md`) 5절이다. 기존 세트에서 쓰던 이름을 따르고, 새 태그는 확인부탁공유 · 보낸메일 둘이다.

### 8.3 작성 절차

1. 입력: 라벨 가이드(`label_guide.md` — 9유형 · 칸별 규칙 · 마감 해석 · 태그 · 보낸 메일 · 파일 형식), 메일 작성 가이드(11절), 위 구성표.
2. 개발셋 v2: Claude로 쓰고 `build.py`로 검증 오류 0을 확인한다. 기존 개발셋 · 오답 유형을 참고해도 된다.
3. 테스트 A · B: **새 Claude 대화**에서 1번 입력만 주고 쓴다. 규칙(`ai/app/pipeline/rules`) · 프롬프트 · 개발셋 · 기존 테스트셋은 보여 주지 않는다. A와 B는 서로 다른 대화에서 쓴다.
4. MailEx에서는 상황만 가져오고 문장 · 이름 · 회사명은 새로 쓴다(D24).

### 8.4 검수 (DE-D17)

- 검수자는 강예은이다. 쓴 사람(최수호 + Claude)과 검수자를 나눈다.
- 봉인 테스트를 검수한 사람은 그 버전 동안 분류 규칙 · 프롬프트 작업을 하지 않는다. 어려우면 테스트 검수는 분류 작업을 하지 않는 팀원(예: 이재운 · 임동하)에게 맡긴다.
- 방법: 세트의 한 줄 요약 목록(`*_mail_list.md`)과 정답을 보며 주 유형 · 할 일 여부 · 할 일 수 · 마감 · 지목을 확인한다. 의견이 갈리면 둘이 정하고, 못 정하면 `tags`에 `애매`를 붙여 보고서에서 따로 센다.
- 검수가 끝난 세트만 봉인 · 측정한다.

### 8.5 봉인 · 보관 · 측정 (DE-D15)

- 테스트 A · B 원본(`mails_test*.py` · JSON · 목록)은 레포 폴더 밖(데이터 파트 PC)에 두고 개인 드라이브에 백업한다.
- 레포에는 세트 이름 · 건수 · 구성표와 JSON 파일의 SHA-256만 남긴다(나중에 바뀌지 않았음을 보이는 용도). 기록 위치는 `sealed_sets.md`.
- 만들기: `cd data/dummy` → `python build.py testA --src <레포 밖 폴더>`. 레포 안 폴더를 주면 `build.py`가 막는다. 출력 마지막 줄이 SHA-256이다.
- 측정은 데이터 파트가 한다: `python eval/runners/run_dummy.py --file <레포 밖 폴더>/testA_mails.json --llm`(DE-4). 결과 · 보고서 · 모델 출력 캐시는 그 폴더에 남고, 레포 안 `--out`은 실행기가 막는다.
- 레포에 올리는 결과는 점수와 유형 · 태그별 정답률까지다. 오답 메일 내용 · 목록은 올리지 않는다.
- 테스트 A 오답을 보고 규칙을 고치면 A는 개발셋으로 내리고 새 A를 만든다. 원본 공개는 IR Day(11/28) 뒤 또는 세트를 바꿀 때 한다.

## 10. 평가 지표 — 채점과 판정 구분

| 항목 | 방식 | 지금 | 할 일 |
|---|---|---|---|
| 주 유형 · 할 일 여부 · 할 일 수 · 마감 · 지목 · 긴급 · 재요청 · 우선순위 | 코드 채점(정답이 하나) | 보고서 0절 한눈 요약(개수로 나눔) · 1~8절 | 버전별 추이표(`scores.md`) |
| 할 일 내용(action 문장) | 판정(표현이 여러 가지) | 글자 유사도(difflib)로 할 일을 짝짓고, 평균 유사도는 보고서 10절(판정 · 참고값)에만 적는다. 내용 판정 · 사람 검수 칸은 `기록 없음` | 독립 에이전트 판정(`eval/judges/`) + 사람 검수 |
| 요약 · 회신 초안 | 판정 | 없음 | DE-6 |
| 모델 비교 | 같은 세트 · 같은 채점기 | 10/24 벤치(8통, 1.2B vs 7.8B) | 규칙만 / 규칙 + 엑사원 7.8B / (참고) 외부 모델(`eval/`에서만, D41), 메일 1통 시간 함께 |

- 보고서는 코드 채점 점수와 판정 점수를 나눠 적는다. 판정 점수는 참고값이고 정답은 코드 채점과 사람 검수가 정한다.
- 보고서 순서(DE-5, `data/dummy/eval.py`): 0절 한눈 요약 → 1~8절 코드 채점 → 9절 확인 칸(임시 기준) · 10절 판정(참고값).
  - 0절은 pr_review 3-1절 형식이다. 할 일 있는 메일 · 없는 메일을 맞음 · 일부 칸 틀림 · 오답(놓침 · 할 일로 잡음)으로 나누고, 할 일 단위(마감 맞음 · 마감 틀림 · 놓친 할 일 · 더 만든 할 일), 틀린 칸별 통수, 목표(DE-D13) 달성 여부를 적는다.
  - 시험 · 봉인 세트(test · test3 · 레포 밖 정답 파일)는 오답 메일 ID · 제목을 적지 않는다(8.5절). 틀린 칸별 통수와 유형 · 태그별 정답률까지만 남는다.

## 11. 메일 작성 가이드 (DE-2 · DE-3)

AI 파트 요청(11/4): 말투와 단어를 실제 회사 업무에서 쓰일 법하게 쓴다.

- 말투: 상급자에게는 "검토 부탁드립니다" · "회신 주시면 감사하겠습니다", 동료에게는 "확인 부탁드려요" · "공유드립니다", 외부 고객사에는 더 격식 있게.
- 용어: 품의 · 결재 상신 · 주간보고 · 회의록 · 산출물 · WBS · 요구사항 정의서 · 착수 / 중간 / 완료보고 · 고객사 · PM / PL · 이행 · 오픈 · 장애 · SR · 형상관리 · 협조 요청.
- 기한 표현: 금일 중 · 익일 오전 · 차주 화요일 · 11/12(목) 18시까지 · EOD · ASAP, 모호한 표현("편하실 때" · "가급적 빨리").
- 형식: RE: · FW: 스레드와 인용된 이전 메일, 서명란, 수신 / 참조 구분, 첨부 언급, FYI 공유 · 자동회신 · 결재 시스템 알림(noreply).
- 헷갈리는 할 일 없는 메일: "확인 부탁드립니다"로 끝나는 단순 공유, 나 말고 다른 사람을 지목한 요청, 이미 끝난 건의 결과 공유, "이상 없으면 회신 생략", 요청 말투의 공지.
- AI-T5에서 쓸데없는 할 일이 나온 유형(완료 · 확정 회신, '[보고] ~ 완료', 지목 없는 전사 공지의 기한 당부)을 개발셋 v2에 넉넉히 넣는다.
- 원칙: MailEx는 상황만 가져오고 문장 · 이름 · 회사명은 새로 쓴다(D24). 인물은 가상 조직(`data/dummy/people.py`)을 쓴다.
- CI에 걸리지 않게(라벨 가이드 8절): IP 주소 모양 글자 · 실제 계정 홈 경로를 쓰지 않는다. 메일 주소는 `.example`, 전화는 `02-0000-xxxx`. MailEx 원본(`data/raw/`)은 올리지 않는다. 메일 정의 파일은 `ruff` 문법 검사를 통과해야 한다.
