## 1. 목표

더미 메일과 정답 라벨을 만들고, 분류 결과(규칙 + 모델)를 채점한다. 모델을 부르는 측정은 오픈라우터 2종으로 한다(DE-D24, 11/7). 서비스 모델은 엑사원 그대로다(D41). 코드 채점 + md 보고서 + 사람 검수로 평가하고(D15), Claude는 코드로 맞히기 어려운 항목의 보조 채점에만 쓴다(D26).

## 6. 완료 기준 (입력 → 기대 결과)

## 7. 위험

- 더미 메일 성능이 실제 메일 성능을 보장하지 않는다.
- MailEx 원문을 번역 · 이름만 바꾸면 원문을 옮긴 것으로 볼 수 있다 `[불확실]` → 상황만 가져와 새로 쓴다.
- Claude 채점은 참고값이다. 정답은 코드 채점과 사람 검수가 정한다.

### 8.4 검수 (DE-D17)

- 검수자는 데이터 · 평가 담당(최수호)이다(11/7). 메일과 정답은 Claude(봉인 테스트는 별도 대화 · 별도 작성자)가 쓰므로 쓴 사람과 검수자는 나뉜다.
- 봉인 테스트를 검수한 사람은 그 버전 동안 테스트에서 본 메일을 근거로 분류 규칙 · 프롬프트 수정을 제안하지 않는다.
- 검수 도구: 세트 폴더(레포 밖)에 검수용 HTML을 두고, 메일마다 체크 · 고칠 것을 적어 결과 문장을 남긴다(테스트 A, 11/7). AI 1차 검토(기준대로 먼저 보고 판단이 필요한 메일만 표시)를 쓸 수 있고, 고칠지는 사람이 정한다. 봉인 세트는 PR에 고친 통수 · 기준까지만 적는다.
- 방법: 세트의 한 줄 요약 목록(`*_mail_list.md`)과 정답을 보며 주 유형 · 할 일 여부 · 할 일 수 · 마감 · 지목을 확인한다. 의견이 갈리면 둘이 정하고, 못 정하면 `tags`에 `애매`를 붙여 보고서에서 따로 센다.
- 검수가 끝난 세트만 봉인 · 측정한다.
- **표준 절차: 독립 재라벨 비교(11/13~, 테스트 A v4 · 테스트 B v1 · 리마인더 신호 세트 #83)**
  1. 세트에서 정답을 뺀 입력만 모은다(메일 · 요청). 봉인 세트는 레포 밖 폴더에서만 만든다.
  2. 별도 에이전트(규칙 · 프롬프트 · 다른 세트 · 원래 정답을 보지 않음)에게 기준 문서(라벨 가이드, 신호 세트는 명세 · 결정 정의)와 입력만 주고 다시 매기게 한다. 확신이 낮은 메일은 기준 문장을 근거로 한 줄 적게 한다.
  3. 원래 정답과 칸마다(주 유형 · 할 일 여부 · 할 일 수 · 마감 · 긴급 · 재요청 · 지목, 신호 세트는 신호 · 날짜 · 이유) 비교해 다른 메일만 뽑는다. 날짜는 요일까지 맞는지 함께 본다.
  4. 다른 메일 · 확신이 낮은 메일만 검수자(최수호)가 기준대로 정한다. 기준 문장으로 정해지지 않으면 원리를 라벨 가이드에 더하고(decisions에 기록, 봉인 세트는 메일 번호 · 내용 없이) 같은 원리를 다른 세트에도 맞춘다. 그래도 갈리면 `애매`.
  5. 기록은 '최수호 N통 검수(AI 1차 검토 활용)'와 같은 통수 · 고친 정답 수로 남긴다. 봉인 세트는 다시 만든 SHA를 `sealed_sets.md`에, 작업 파일은 세트 폴더 `work\`에 둔다(클라우드 · 채팅에 남기지 않는다).
  - 결과: 테스트 B 80통 중 78통 · 신호 세트 39통 중 36통이 두 작성자 정답이 같았다. 다른 메일에서 원리 2가지(DE-D28 10번)와 요일 오기 1곳 · 날짜 표현 1가지(#83 리뷰)를 찾았다.

### 8.5 봉인 · 보관 · 측정 (DE-D15)

- 테스트 A · B 원본(`mails_test*.py` · JSON · 목록)은 레포 폴더 밖(데이터 파트 PC)에 두고 개인 드라이브에 백업한다.
- 레포에는 세트 이름 · 건수 · 구성표와 JSON 파일의 SHA-256만 남긴다(나중에 바뀌지 않았음을 보이는 용도). 기록 위치는 `sealed_sets.md`.
- 만들기: `cd data/dummy` → `python build.py testA --src <레포 밖 폴더>`. 레포 안 폴더를 주면 `build.py`가 막는다. 출력 마지막 줄이 SHA-256이다.
- 측정은 데이터 파트가 한다: `python eval/runners/run_dummy.py --file <레포 밖 폴더>/testA_mails.json --llm`(DE-4). 결과 · 보고서 · 모델 출력 캐시는 그 폴더에 남고, 레포 안 `--out`은 실행기가 막는다.
- 레포에 올리는 결과는 점수와 유형 · 태그별 정답률까지다. 오답 메일 내용 · 목록은 올리지 않는다.
- 테스트 A 오답을 보고 규칙을 고치면 A는 개발셋으로 내리고 새 A를 만든다. 원본 공개는 IR Day(11/28) 뒤 또는 세트를 바꿀 때 한다.

- 형식: RE: · FW: 스레드와 인용된 이전 메일, 서명란, 수신 / 참조 구분, 첨부 언급, FYI 공유 · 자동회신 · 결재 시스템 알림(noreply).
- 헷갈리는 할 일 없는 메일: ("확인 부탁드립니다"로 끝나는 공유는 11/6부터 할 일 — 라벨 가이드 5절 확인부탁공유) 나 말고 다른 사람을 지목한 요청, 이미 끝난 건의 결과 공유, "이상 없으면 회신 생략", 요청 말투의 공지.
- AI-T5에서 쓸데없는 할 일이 나온 유형(완료 · 확정 회신, '[보고] ~ 완료', 지목 없는 전사 공지의 기한 당부)을 개발셋 v2에 넉넉히 넣는다.
- 원칙: MailEx는 상황만 가져오고 문장 · 이름 · 회사명은 새로 쓴다(D24). 인물은 가상 조직(`data/dummy/people.py`)을 쓴다.
- CI에 걸리지 않게(라벨 가이드 8절): IP 주소 모양 글자 · 실제 계정 홈 경로를 쓰지 않는다. 메일 주소는 `.example`, 전화는 `02-0000-xxxx`. MailEx 원본(`data/raw/`)은 올리지 않는다. 메일 정의 파일은 `ruff` 문법 검사를 통과해야 한다.
