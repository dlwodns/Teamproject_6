## 1. 어느 문서에 무엇을 쓰나

| 내용 | 위치 |
|---|---|
| 여러 파트에 걸친 결정 | `00_common/decisions.md` (`D` 번호) |
| 한 파트 안의 결정 | `<파트>/decisions.md` (`FE-D` 등) |
| 한 일 (날짜순) | `00_common/log.md` |
| 지금 상태 · 다음 할 일 | `00_common/handoff.md` |
| 막혔던 문제와 해결 | `<파트>/troubleshooting.md` |
| 작업 순서 · 담당 · 기한 | `<파트>/plan.md` |
| 기능 상세 명세 (PRD를 구현 단위로 풀어 쓴 것) | `<파트>/detail.md` |

- 다른 파트에 영향을 주는 결정은 공통 decisions에 쓰고, 영향받는 파트 decisions에는 번호만 연결한다.
- 문체는 보고서체(~다)로 쓴다. 확인하지 못한 내용은 `[불확실]`, 출처 없는 수치는 `[미확인]`을 붙인다.

## 2. 브랜치 · 커밋 · PR

1. 작업 전 `10_planning/refs/PRD.md`와 자기 파트 `plan.md`를 읽는다.
2. 브랜치 이름: `feature/기능명` · `fix/수정내용` · `docs/문서명`을 쓰고, 기능명 앞에 작업 번호를 붙인다 (예: `feature/FE-3-dashboard`, `fix/BE-2-dummy-load`). (D32 · D33)
   - 파트 문서 브랜치는 `feature/<파트 약어>`(예: `feature/AI` · `feature/PL`)로 둔다. 여러 파트가 함께 보는 문서(`00_common/` · PRD · README · `.env.example` · `eval/README.md`)는 main에서 고치고, log · handoff는 main에서만 고친다. (2026-11-02)
3. 한 번에 작은 변경 하나만 한다. 기존 API · DB · 저장 방식은 합의 없이 바꾸지 않는다.
4. 커밋 메시지는 노션 팀 규칙 `유형: 요약`을 따르고 요약 앞에 작업 번호를 넣는다 (예: `feat: FE-3 업무 칸 렌더링`). (D32)
5. AI는 commit까지만 한다. push와 PR 생성은 사람이 한다.
6. 커밋 작성자는 사람 한 명이다. Co-Authored-By를 넣지 않는다.
7. AI 도움을 받았으면 PR 본문 '작성 방식'에 적는다 (예: 작성자의 아이디어를 Claude로 템플릿화해 초안을 잡고 구체화했다).
8. PR 본문에 확인 방법(입력 → 기대 결과)과 리뷰어를 적는다.

## 3. 기여도 표기

모든 결정 · 트러블슈팅 항목 아래에 한 줄을 둔다.

```
- 상태: 채택 · 제안: 홍길동 · 결정: 김철수 · 리뷰: 이영희 · 공동: — · 근거: D14, AI-T2
```

| 칸 | 뜻 |
|---|---|
| 제안 | 아이디어 · 대안을 처음 낸 사람 |
| 결정 | 채택 · 보류 · 기각을 정한 사람. 파트 결정은 파트 담당, 공통 결정은 팀 회의 |
| 리뷰 | 내용을 검토하고 의견을 남기거나 승인한 사람 |
| 공동 | 함께 작성 · 구현한 사람 |
| 근거 | 바탕이 된 결정 · 조사 · 트러블슈팅 번호 |

- 여러 명이면 쉼표로 쓴다. 비어 있으면 `—`, 아직 정하지 못했으면 `[미정]`.
- 트러블슈팅은 `발견 · 해결 · 리뷰 · 공동`을 쓴다.
- 구현 기여는 PR로 센다(작성자 · 리뷰어). 주 1회 `contribution.md`에 모은다.

## 4. 상태 흐름

```
제안 → 검토 중 → 채택 / 보류 / 기각
채택 → 대체됨(새 번호로)   ← 내용을 바꿀 때는 지우지 않고 새 번호를 만든다
```

## 5. 파트 담당이 정해지거나 바뀔 때

1. 기존 결정(D1~)은 지우지 않는다. 기존 결정의 제안 · 결정자는 그대로 둔다.
2. 새 담당은 자기 파트 `decisions.md`의 '도입 제안' 목록을 확인하고, 항목마다 채택 · 보류 · 기각을 정한다. 이때 결정 칸에 새 담당, 제안 칸에 원래 결정자를 적는다.
3. 담당이 아닌 사람의 아이디어는 '제안' 상태로 올리고, 담당이 리뷰 후 정한다.

## 6. 리뷰 규칙 `[제안]`

- 파트 결정: 파트 담당 결정 + 다른 팀원 1명 이상 리뷰
- 다른 파트에 영향을 주는 결정: 영향받는 파트 담당 리뷰 필수
- 공통 결정: 팀 회의 또는 팀장 · 테크팀장 리뷰
- PR: 작성자 외 1명 승인 후 병합. main 직접 푸시 금지. 리뷰 · 머지 절차와 체크리스트는 `pr_review.md`

## 7. 보안

- API 키 · 토큰 · 비밀번호는 코드와 문서에 쓰지 않는다. `.env`에만 둔다.
- 실제 사내 메일 · 개인 메일 · 실명 데이터는 레포에 넣지 않는다. MailEx 원본은 `data/raw/`에만 둔다(D24).
- Claude는 `eval/`에서만 쓴다(D26).
