## 2. 역할 분담 `[제안]`

| 단계 | 담당 | 내용 |
|---|---|---|
| PR 생성 | 작성자 본인 | push · PR 생성, 리뷰어 지정 |
| 리뷰 | 작성자 외 1명 이상 | 같은 파트 팀원 우선, 다른 파트에 영향 주는 변경은 그 파트 담당 포함 |
| 머지 | 리뷰 승인 후 작성자 또는 레포 관리자 | 승인 없는 머지 금지, 본인 승인으로 머지 금지 |
| 기록 | 작성자 | 결정 · 트러블슈팅 문서 반영, `contribution.md` 집계 대상 |

- 작성자가 혼자 PR 생성 · 승인 · 머지까지 하는 방식은 노션 규칙 "PR 및 리뷰 후 병합"과 맞지 않음.

## 3. PR 올리기 전 (작성자)

- [ ] 최신 main 반영 후 충돌 없음
- [ ] 한 PR에 변경 하나 (작업 번호 1개 기준)
- [ ] 로컬 실행 · 테스트 통과, 확인 방법(입력 → 기대 결과) 작성
- [ ] 키 · 토큰 · 실제 메일 · 실명 데이터 없음, `.env` 미포함
- [ ] `frontend/` · `backend/`에 Claude 호출 없음 (D26)
- [ ] 커밋 작성자 본인 1명, Co-Authored-By 없음
- [ ] 결정이 생겼으면 파트 `decisions.md`, 막힌 문제는 `troubleshooting.md` 반영
- [ ] PR 본문 기여 칸(작성 · 공동 · 리뷰 요청 · 작성 방식) 작성
- [ ] 평가 · 실측 결과가 있으면 3-1 형식(개수 분해 · 생략 없음 · 기록 없음 표시)으로 표 작성

### 3-1. 결과 기록 형식 (PR 본문 · plan · troubleshooting · log · handoff 공통) `[제안: 문규남 11-03]`

처음 보는 사람이 표만 보고 바로 이해하는 것이 기준. 비율만 적지 않고 **정답 개수를 결과별 개수로 나눠** 적음.

| 규칙 | 내용 | 예 |
|---|---|---|
| 개수 분해 | 해야 할 것 N개 → 맞게 함 / 일부 틀림 / 다른 것으로 함(오답) / 놓침. 하면 안 되는 것 M개 → 바르게 거름 / 걸렀으나 이유 틀림 / 해 버림(오답) · 그중 위험한 것 | 명령 70개 중 맞게 바꿈 47 · 일부 틀림 4 · 다른 행동 3 · 놓침 16 |
| 단위 분리 | 메일 단위와 할 일 단위를 따로 적음. 메일 단위 놓침 0이어도 할 일 단위 놓침이 있을 수 있음 | 놓친 할 일 메일 0통 · 놓친 할 일 1개 |
| 합계 · 쪼갬 | 종류별 · 행동별 표와 합계 행을 붙여 합이 맞는지 보이게 함 | 행동 T01~T14 표의 합 = 70 |
| 표 읽는 법 | 표 위에 이 표가 보여 주는 것 한 줄. 지표 · 세트 뜻은 먼저 풀어 둠(뜻 · 좋은 쪽) | 할 일 메일 정밀도 = 할 일 있다고 판정한 메일 중 실제 할 일 메일 비율, 높을수록 |
| 쉬운 열 이름 | 약어 · 영문 대신 쉬운 말, ↑↓로 좋은 방향, 단위(통 · 개 · 초 · %) 표시 | Task 재현율 → 할 일 메일 재현율 ↑ |
| 한 칸 한 숫자 | 한 칸에 여러 숫자를 몰아 넣지 않음. 전후 비교는 '전 → 후' | `51 · 위험 6 · 정상 30/70` 금지 |
| 생략 없음 | 버전별 · 세트별 결과, 넣지 않은 안과 이유까지 모두 적음. 개발 세트(낙관적)와 시험 세트 구분 | — |
| 기록 없음 | 측정하지 않은 값은 지어내지 않고 `기록 없음`. 계산한 값은 `*` 표시, 다시 잰 값은 다시 쟀다고 밝힘 | 정밀도로 역산한 값 `3*` |
| 봉인 세트 | 시험 · 봉인 세트를 다시 재야 하면 먼저 팀(파트)에 확인 | — |

## 4. 리뷰할 것 (리뷰어)

| 구분 | 확인 내용 |
|---|---|
| 범위 | 작업 번호 · `plan.md`와 일치, 범위 밖 변경 없음 |
| 동작 | PR에 적힌 확인 방법 직접 실행, 기대 결과와 일치 |
| 계약 | API · DB · 응답 형식 변경 시 상대 파트 합의 여부 (`plan.md` 5절 접점) |
| 보안 · 개인정보 | 비밀값 · 실제 메일 · 실명 데이터 없음, 로그에 메일 본문 미기록, 엑사원 호출 전 개인정보 가림 |
| 경계 | 실서비스 코드의 Claude · `eval` 의존 없음 |
| 기록 | 관련 결정 · 트러블슈팅 번호 연결, 기여 칸 작성, 결과 표가 3-1 형식(개수 분해 · 합계 일치 · 기록 없음 표시) |

- 결과는 GitHub 리뷰로 남김: 승인(Approve) / 수정 요청(Request changes) / 의견(Comment).
- 수정 요청 시 이유와 기대하는 수정 방향 함께 기록.
