## 1. 설계 원칙

1. 에이전트는 **정해진 행동 목록 안에서만** 고른다. 목록 밖 요청은 "지원하지 않는 요청"으로 응답한다 `[확정]` (D27).
2. 행동 하나 = 이름 · 입력 형식 · 유형 · 확인 규칙 · 되돌리기 여부를 가진 **도구 정의 1개**.
3. 도구 정의는 한 곳(백엔드 행동 레지스트리, `backend/app/agent/tools/`)에만 둔다. 웹 에이전트 · REST 버튼 · MCP 서버가 같은 정의를 쓴다. ai는 `/agent/plan` 요청에 실려 온 목록만 본다.
4. 실행은 백엔드 코드가 한다. 모델은 "어떤 행동을, 어떤 대상에" 고르는 일만 한다 (D34).
5. 모든 행동은 `action_log`에 기록한다 → 되돌리기와 처리 이력 추적의 근거.
6. 서비스 경로의 모델은 엑사원 하나다. 외부 LLM 호출 경로를 두지 않는다 `[확정]` (D41). 11-02 작성 때는 로컬 `EXAONE-3.5-7.8B-Instruct-GGUF:Q4_K_M`(D44)이었고, 11-14부터 엑사원 API의 K-EXAONE 2.5(`k-exaone_v2.5`)다(D51 · D52 · AI-D18).

### 2.1 레지스트리 정의 형식 `[제안]`

ActionDef(
    id="T05",
    name="나중에_처리",
    kind="state_change",          # query | display | state_change | settings | send
    target_schema={"mail_ids": list[int], "sender": str | None, "category": str | None, "date_range": str | None},

    undoable=True,
    side_effects=["reminder.schedule"],

- **T02 · T05 `target.status`(11-18)**: '끝낸 거'는 `done`, '미룬 거'는 `snoozed`. 없으면 미처리(pending · snoozed). `done`에 기간이 있으면 끝낸 날(`done_at`)로 거른다. 다른 행동에서는 비운다.

- **T15 값 채우기(AI-D16, `agent_rules_v1.5` `event_params`)**:
  - 날짜 · 시각은 메일 회의 시각과 **같은 코드**로 읽는다(`ai/app/pipeline/dates.py`의 `parse_event_at` · `parse_event_end`). 명령과 메일에서 같은 글자는 같은 시각이 된다(테스트 `test_command_and_mail_use_same_clock`).
  - `start`: 날짜와 시각 글자가 함께 있으면 그 시각. 날짜 없이 시각만 있으면 오늘, 이미 지났으면 내일. 날짜만 있거나 '오전에'처럼 때만 있으면 null이고, ai는 실행 대신 되묻는다(`reason = ambiguous`). 18:00 같은 기본 시각을 넣지 않는다.
  - 날짜로 못 읽는 상대 시점('3일 뒤 · 다음 주에 · 주말에')만 있으면 오늘로 두지 않고 되묻는다. 마감 표지가 붙은 시각('17시 마감 전 · 18:00까지')은 일정 시각으로 쓰지 않는다.
  - `end`: 시작 시각과 같은 시각으로 시작하는 범위를 말했을 때만 둔다. 시작보다 늦은 가장 이른 시각을 고르고, **자정을 넘으면 다음 날이다**('23:30~00:30' → 다음 날 00:30, '22:00~24:00' → 다음 날 00:00). 12시간을 넘는 범위는 버린다. null이면 backend가 시작부터 1시간으로 둔다(D50).
  - `title`이 null이면 고른 메일 제목, 그것도 없으면 '일정'이다.
  - 초안(T07 · T12)과 한 문장에 함께 시키면('회신 초안 쓰고 내일 10시 회의 잡아줘') 하나만 실행하지 않고 `ambiguous`로 되묻는다. `candidates`에 두 행동이 들어간다.
  - T15는 backend가 허용 목록(`actions`)에 넣었을 때만 규칙 후보가 된다. 넣기 전에는 일정 등록 지시가 이전처럼 '지원 외'이고, 다른 행동의 결과도 v1.4와 같다(봉인 명령 평가 366문장 차이 0건).
- **[계약] 고른 메일 · 카드 버튼 · 자동 등록에서 backend가 시각을 채울 때** `[확정: 문규남 11-10]`:
  1. `start`가 null이고 고른 메일이 있으면, backend는 그 메일 **일정참석 할 일의 `due_time_stated`가 true일 때만** 그 할 일의 `due_at`(과 `end_at`)을 쓴다.
  2. `due_time_stated`가 false이거나 `due_at`이 null이면 **`due_at` 값(18:00 등 보정값)을 일정 시각으로 쓰지 않는다.** 일정을 만들지 않고 "몇 시에 넣을까요?"로 되묻는다. 일정참석 할 일이 없는 메일도 같다.
  3. 일정 참석 카드의 [캘린더에 넣기]도 같은 규칙이다. 시각이 적히지 않은 메일이면 버튼을 누른 뒤 시각 고르기를 띄우고, 보정값을 미리 채워 두지 않는다.
  4. 자동 등록은 `due_time_stated`가 true인 일정참석 할 일만 넣는다(아래 '분류 응답의 시각 표시').
- **분류 응답의 시각 표시(AI-D16)**: `/classify`의 `tasks[]`에 `due_time_stated`(bool)와 `end_at`(일정참석만)이 있다. `due_time_stated`는 `due_at`의 시각이 메일에 글자로 있었으면 true, 날짜만 있어 기본 시각(18:00 · 12:00 · 09:00)으로 채웠거나 기한이 없으면 false다.
  - 일정참석 할 일은 마감 표지가 붙은 시각을 회의 시각으로 보지 않는다. '주간 회의 참석 여부를 11/12(목) 18:00까지 회신'에서 회의 할 일은 false다. 같은 글자라도 회신요청 할 일의 기한으로는 true다(시각이 적힌 기한). 그래서 backend 자동 등록은 **할 일 유형이 일정참석인지도 반드시 함께 본다.**
  - backend 캘린더 자동 등록은 일정참석이고 이 값이 true이며 시각이 아직 오지 않은 일정만 넣는다(`docs/10_planning/suggestion_cards.md` 3.3절).
- **행동 ID(T01~T20)와 params 키는 backend · ai 공동 계약이다. 고정하며, 바꾸면 backend 레지스트리와 `ai/app/agent/rules_v1.py`(`extract_params`)를 같은 PR 묶음에서 함께 고친다.** 위 params 열은 구현(agent_rules_v1.4) 기준이다. 값이 없으면 키를 비우지 않고 `null`로 둔다(예: T05 `until`). (PR #4 리뷰 반영, 11-04, 공통 D47)
- ai는 레지스트리 목록(`actions`)에 없는 ID는 고르지 않는다(D27). backend는 ai가 돌려준 ID를 레지스트리에서 다시 찾고, 없으면 실행하지 않는다.

## 3. 행동 유형과 확인 정책 `[확정]` (D37)

| 유형 | 예 | 확인 | 되돌리기 |
|---|---|---|---|
| 조회 | 오늘 요약, 미처리 조회, 무응답 확인 | 없음 | 해당 없음 |
| 표시 | 회신 초안, 초안 작성 (발송 안 함) | 없음 | 해당 없음 |
| 상태 변경 1건 | 1건 완료, 1건 나중에 처리 | 없음, 실행 후 되돌리기 알림 | 가능 |
| 상태 변경 2건 이상 / 대상 후보 여러 개 | 일괄 완료 | **확인창** | 가능 |
| 설정 변경 | 리마인드 주기, 중요 발신자 | **확인창** | 가능 |
| 발송 | 템플릿 전송 | **항상 미리보기 + 확인** | **불가** (확인창에 명시) |

- 판정은 **백엔드 규칙**이 한다. 모델 출력에 확인 여부를 넣지 않는다.
- 판정 입력: 행동 `kind` + 대상 해석 결과 건수. 대상 후보가 여러 개(예: "견적 건"이 3건에 걸림)이면 1건 변경이어도 확인창에서 고르게 한다.

## 4. 명령 해석

### 4.1 흐름 `[확정 방향]` (D44)

1. **규칙 매칭**: 키워드 · 문장 패턴으로 행동 1개가 정확히 걸리면 확정한다(`source = rule`).
2. 0개 또는 2개 이상 걸리면 **엑사원 + 예시 문장**으로 판단한다(JSON 출력, `source = model`).
   - 11-13 바뀜(AI-D19, `agent_v1.3`~): 1 · 2 대신 **모든 지시를 엑사원이 먼저 읽고** 행동을 고른다. 규칙(`agent_rules_v1.7`)은 허용 목록 · 값 계산 · 빠진 값 되묻기 · 상태 변경 전 확인 · 지원 외 메일 조작 거르기만 맡는다(`ai/app/agent/plan.py` 머리말).
3. **검증**: 허용된 행동 이름이 아니거나 JSON 형식이 틀리면 "지원하지 않는 요청".
4. **대상 해석**: 발신자명은 DB(`contacts`) 매칭. "이거 · 아까 그 메일" 같은 지시어는 프론트가 현재 선택한 메일 ID(`selected_mail_ids`)를 함께 보낸다.
5. **확인 정책** 판정(3절)은 백엔드 규칙이 한다.
6. 실행 → `action_log` 기록 → 결과 카드 표시.

- 1~3은 ai `/agent/plan`, 4~6은 backend가 한다(구조도 v3.1 6절).
- 충돌 규칙: 과거형 완료 표현이 우선한다 ("회신 다 했어" → T03 일괄_완료, T07 회신_초안 아님).

### 4.2 규칙 초안 `[제안]`

| 행동 | 패턴 예 (정규식은 구현 시) |
|---|---|
| T01 | "오늘" + ("뭐 해야" \| "할 일" \| "요약") |
| T03 | ("다" \| "전부" \| "모두")? + ("처리했" \| "끝냈" \| "완료했" \| "했어") — 과거형 |
| T04 | "취소" \| "되돌려" \| "방금 거" |
| T05 | ("다시 알려" \| "나중에" \| "미뤄") + 날짜 표현 |
| T06 | ("답장" \| "회신") + ("안 온" \| "없는" \| "안 왔") |
| T14 | ("재촉" \| "독촉" \| "다시 요청") + ("메일" \| "보내") → 재촉 템플릿. "템플릿" + "보내" → 일반 템플릿 |
| T07 | ("회신" \| "답장") + "초안" + 지시어 |
| T10 | "빼" \| "제외" |
| T13 | "기한" + ("보여" \| "언제") |
| T15 | ("캘린더" \| "달력" \| "일정") + ("에" \| "로") + ("넣어" \| "등록" \| "추가" \| "잡아") · ("회의" \| "미팅" \| "일정" \| "약속" …) + ("잡아" \| "등록해" \| "만들어") — 시키는 꼴만. '일정 잡는 메일'은 T12다. T15가 걸리면 T13(캘린더 보기)을 지운다 |

- 날짜 표현("금요일", "이번 주", "다음 주 초")은 분류 파이프라인 후처리와 같은 코드로 환산한다(수신일 · 현재 시각 기준).
- 규칙과 예시는 버전 파일로 둔다(`ai/app/prompts/agent_v1.*`, `ai/app/pipeline/rules/agent_rules_v1.*`).

### 4.3 엑사원 프롬프트 · 예시 `[제안]`

- 입력: 행동 목록(ID · 이름 · 설명 · 예시 2~3개) + 지시 글자 + 맥락(현재 시각 · 선택 메일 수). 메일 본문은 넣지 않는다.
- 출력: 4.4 JSON. JSON 스키마를 강제하고 `temperature=0`. 11-14부터 엑사원 API 호출부(`ai/app/llm/client.py`)의 JSON 스키마 응답이다(작성 때는 ollama `format`).
- 예시 세트(프롬프트용)와 테스트 세트(평가용)는 분리하고 문장 중복 0건을 지킨다.

### 4.4 출력 형식

```json
{
  "action": "T03",
  "action_name": "일괄_완료",
  "target": { "sender": "김 팀장", "category": null, "date_range": null, "keyword": null, "mail_ids": [], "awaiting_reply": false },
  "params": {},
  "source": "rule | model"
}
```

- 구현(AI-11)에서 `action`은 행동 ID만, 이름은 `action_name`으로 나눴다. backend 레지스트리가 ID로 찾고, 명령 테스트 세트도 ID로 채점하기 때문이다. `keyword`(예: '견적 건')와 `awaiting_reply`(무응답 목록 전체 재촉, T14)를 더했다. 형식 정의는 `ai/app/schemas/agent.py`.
- T05에서 시각이 없는 날짜("금요일에 다시 알려줘")는 아침 알림 시각 08:30으로 둔다(기획 detail 4.2).
- 시각 · ID 형식(PR #4 리뷰 반영, 11-04, 공통 D47, `ai/app/schemas/common.py`): `context.now`는 시간대가 붙은 값(`+09:00` · `Z`)도 받아 KST로 바꾼 뒤 시간대를 떼고 쓴다. 시간대 없는 값은 KST로 본다. 응답 시각(`params.until`)은 시간대 없는 KST다. `selected_mail_ids` · `last_result_ids`는 정수 id도 받고, ai 안과 응답(`target.mail_ids`)에서는 문자열이다. `/classify` · `/summarize`도 같다.

- 지원하지 않는 요청: `{"action": null, "reason": "unsupported", "source": "rule | model"}`.
- `category` 값은 분류 5개(회신 · 요청 · 검토 · 공지 · 기타, D39) 중 하나 또는 null.

### 4.5 2단계 실행 (미리보기 → 확인)

- 확인이 필요한 행동은 먼저 `preview`를 돌려준다: 대상 목록, 바뀔 상태, `preview_id`.
- 사용자가 확인하면 `execute(preview_id)`로 실행한다. `preview_id`는 한 번만 쓸 수 있고 만료 시간이 있다(`action_previews`).
- 웹 UI와 MCP가 같은 방식을 쓴다 → MCP 클라이언트도 확인 없이 일괄 변경할 수 없다.

## 5. MCP 연동 설계

### 5.1 목적

LG CNS 에이전틱웍스가 MCP 방식으로 외부 서비스를 연동한다 → 우리 기능을 MCP 서버로 노출하면 **LG 사내 에이전트 플랫폼에 그대로 꽂히는 구조**를 보여 줄 수 있다. 실제 연동 접근 권한은 없으므로 시연은 일반 MCP 클라이언트로 한다.

### 5.2 구조

```
[행동 레지스트리] ── 도구 정의 1곳 (이름 · 입력 스키마 · 유형 · 확인 규칙)
      │
      ├── 웹 에이전트 (명령 해석 → preview/execute)
      ├── REST API (프론트 버튼)
      └── MCP 서버 (같은 도구를 MCP tool로 노출)
```

- 구현: Python MCP SDK, FastAPI와 같은 프로세스 또는 별도 엔드포인트 `[제안]`. 백엔드가 FastAPI로 확정돼(D38) 같은 언어로 붙일 수 있다.
- 지금 할 일: **레지스트리 구조만 먼저** 만든다(비용 거의 없음). MCP 서버 자체는 P2.
- 11-27 현재: 도구 레지스트리(`backend/app/agent/tools/registry.py`)에 행동마다 MCP 노출 이름(`mcp_tool`)과 `action_log.source = mcp`까지 준비했다. MCP 서버 구축은 아직이다(BE-17, `docs/30_backend/plan.md`).
- MCP 경로는 명령 해석(ai)을 거치지 않는다. MCP 클라이언트가 도구와 인자를 직접 고르므로, 백엔드는 같은 검증 · 확인 정책만 적용한다.

### 5.3 노출 도구 (1차)

| MCP tool | 대응 행동 | 비고 |
|---|---|---|
| `list_pending` | T02 | 조회 |

| `list_awaiting_reply` | T06 | 조회 |

### 5.4 보안 규칙

- MCP 접근 토큰 필수(`.env` `MCP_ACCESS_TOKEN` 자리표시자), 사용자 단위 권한.
- 상태 변경은 반드시 `preview → execute` 2단계.
- 메일 **본문은 기본으로 반환하지 않는다**. 제목 · 발신자 · 기한 · 분류 · 근거 문장만.
- 발송 도구(템플릿 전송)는 MCP에 노출하지 않는다 `[제안]`.
- MCP를 거친 실행은 `action_log.source = mcp`로 기록한다.

- "공지 메일 다 처리했어"는 D40(공지는 업무를 만들지 않음)과 만나면 대상 업무가 0건일 수 있다. 이때는 "해당하는 미처리 업무가 없습니다"로 응답하고 상태를 바꾸지 않는다 `[제안]`.
