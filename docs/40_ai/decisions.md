### AI-D9 · 개발 서버에서는 엑사원을 PC에서 돌리고, 서버는 터널로 부른다 (2026-11-02)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남 · 리뷰: [미정] · 공동: — · 근거: AI-T4 · D41 · D44
- 결정: dev-server-02의 ai 서비스 · 평가는 PC(LG gram) ollama의 `EXAONE-3.5-7.8B-Instruct-GGUF:Q4_K_M`을 쓴다. 서버에는 엑사원 7.8B · llama-server를 띄우지 않는다.
- 결정: 연결은 PC → 서버 역방향 SSH 터널이고, 서버 쪽 출구는 TCP 포트가 아니라 내 홈의 0700 폴더 안 Unix 소켓(`~/run/exaone/ollama.sock`)이다. ollama는 PC의 127.0.0.1에만 연다.
- 결정: 실행은 `scripts/exaone-pc.sh run <명령>`으로 한다. 모델 digest · ollama 버전 고정값(`scripts/exaone-pc.env`)은 선택이다. 비어 있으면 경고만 내고, 채우면 다를 때 실행기가 멈추고 ai 서비스는 엑사원을 부르지 않는다. 11-03 기록값: digest `099a498b9cbf…` · ollama 0.34.0.
- 근거: 서버 user41 메모리 한도 5 GiB에 7.8B(4.5 GB)와 VS Code가 함께 올라가지 않는다. 2.4B는 서버에서 돌지만 벤치 v2에서 할 일 메일 1통을 놓쳤다(D15 위반). PC는 10/24 벤치 환경과 같아 평가 점수를 그대로 비교할 수 있다.
- 대안: 서버에서 2.4B 실행 — 정확도가 떨어져 기각. 서버 TCP 포트로 터널 — 같은 서버의 다른 계정이 붙을 수 있어 기각.
- D41(외부 LLM 경로 없음): PC도 팀이 관리하는 로컬 실행기이고 전송은 SSH로 암호화된다. 공통 결정에 반영할지는 팀 확인 `[결정 필요]`.
- 위험 · 남은 일: PC가 꺼지면 서비스는 규칙 결과만 낸다. 11/14 실배포 · IR Day 시연 때 모델 실행 위치(PC 상시 가동 또는 서버 메모리 한도 상향)는 미결 #6(detail 8절)에서 정한다 `[결정 필요]`.

### AI-D10 · 엑사원을 쓸 수 있으면 모든 메일을 엑사원에도 묻고, 규칙과 서로 보완해 합친다 (2026-11-05)

- 상태: **AI-D15로 대체(11/7)** — 모든 메일을 모델에 묻는 것은 그대로, 규칙과 합치기는 없앴다 · 제안: 문규남 · 결정: 문규남 · 리뷰: [미정] · 공동: — · 근거: D14 · D15 · plan 4.8절 · AI-T10
- 결정: `ROUTER_MODE=all`(기본). 규칙 결과는 늘 만들고, 엑사원 결과와 원칙대로 합친다. 엑사원이 꺼지면 규칙 결과만 낸다. `gate`(v3.2 문지기, 애매한 메일만 엑사원)는 비교 · 느린 장비용으로 남긴다. 그 밖의 값이면 ai 서비스가 시작하지 않는다(`LLM_BACKEND`도 같음, #21 리뷰).
- 합치기 원칙: 규칙만 찾은 할 일은 남긴다(D15). 엑사원이 더 낸 할 일이 나를 향하지 않은 문장('전 임직원은 ~')에서 나왔거나, 대상자 당부 공지 · '참고만 해 주세요' · 선택 요청('의견 있으신 분은') 메일에서 엑사원만 만든 할 일이면 확인 칸으로. 기한은 요청 문장에 붙은 규칙 기한을 먼저, 엑사원 기한은 마감 표지로 다시 확인. 단, 엑사원이 기한을 찾은 할 일은 같은 요청일 때만 규칙 기한으로 덮는다 — 둘 다 할 일 1개이거나, 규칙 할 일 하나당 가장 닮은 엑사원 할 일 하나(한글 bigram 절반 이상 겹침)만(#21 리뷰, 11/7). 유형은 요청 문장의 콕 집는 단서 > 메일 성격(kind) > 엑사원. 마지막에 유형과 할 일 여부를 맞춘다.
- 근거: 11/5 같은 엑사원 출력으로 비교했을 때 test에서 모든 메일 방식은 놓침 0, 문지기 방식은 1. 사용자 기준 '5~10분 늦어도 되지만 틀린 정보가 더 나쁘다'(11/5).
- 대안: 문지기 방식 유지 — 처음 보는 메일에서 누락이 남아 기각. 엑사원만 쓰기 — 공지 · 회신에 할 일을 만드는 버릇(AI-T5)이 그대로라 기각.
- 비용: PC CPU에서 메일 1통 약 28초(11/5 실측). 동기 요청으로 기다리지 않고 대기열로 처리한다. 동시 처리 · GPU 서빙은 미결 #6(detail 8절)에서 측정 후 정한다.

### AI-D14 · 할 일마다 본문에 글자 그대로 있는 근거 문장을 붙인다 — AI-15 보류 해제 (2026-11-07)

- 상태: 채택(ai 쪽) · 제안: 문규남 · 결정: 문규남(사용자 지시 11/7 "AI-15 보류 해제, 근거 문장을 잘 뽑는지 · 문제 없이 동작하는지 확인 후 진행") · 리뷰: [미정] · 공동: BE(`tasks.evidence_text` 저장) · FE · UX(UX-D16 형광펜) · 근거: 기획 detail 14절 #4(권장 '해제') · #5(근거 문장만 저장) · AI detail 8절 #4 · plan 4.9절
- 문제: `/classify` 응답 `tasks[].evidence`는 규칙 경로에서만 찼다. 기본 경로인 모든 메일 엑사원(AI-D10)은 할 일 문구를 엑사원 것으로 쓰는데 근거를 붙이지 않아 **개발 세트 할 일 247개 중 근거가 있는 것은 0개**였다. 규칙 근거도 252개 중 35개는 본문에서 그대로 찾을 수 없었다 — 줄이 다른 요청 문장을 공백으로 이어 붙인 것 20개, 요청 문장이 없는 회의 초대에서 제목을 근거로 둔 것 15개.
- 결정(형식): `evidence` = **본문에 글자 그대로 있는 문장을 줄바꿈(`\n`)으로 이은 것**, 못 찾으면 `null`. 화면은 줄마다 본문에서 찾아 칠하고, 못 찾은 줄은 칠하지 않는다. 틀린 곳을 칠하는 것보다 칠하지 않는 것이 낫다. 응답 형식(`str | None`)은 그대로라 ai · backend 스키마는 바꾸지 않는다.

  2. 자정을 넘는 끝 시각: 끝 시각 후보(그 시각 · 12시간 뒤 · 다음 날) 중 시작보다 늦은 가장 이른 것. '23:30~00:30'은 다음 날 00:30, '22:00~24:00'은 다음 날 00:00. 콜론 시각은 24시간제, 12시간을 넘는 범위는 버린다. '새벽 2시'를 오후로 바꾸지 않게 `새벽`을 시각 앞말로 더했다(이전에는 14:00이 됐다).
  3. 고른 메일 · 카드 버튼에서 backend가 시각을 채울 때 `due_time_stated=false`면 보정값(18:00)을 쓰지 않고 되묻는다 — AI detail 2.1절 '[계약]'.
  4. 명령과 메일이 같은 코드로 날짜 · 시각을 읽는다(`parse_event_at` · `parse_event_end`, 명령만 `roll_forward`로 날짜 없는 시각을 오늘 · 내일로). 날짜로 못 읽는 상대 시점('3일 뒤 · 다음 주에 · 주말에')만 있으면 오늘로 두지 않고 되묻는다(이전 구현은 오늘 14:00으로 넣었다).
  5. T15를 허용한 테스트: `tests/test_agent_t15.py`가 허용 목록에 T15를 넣고 `/agent/plan` 엔드포인트로 실행 · 고른 메일 · 되묻기 4종 · 모델 경로 · 모델이 골라도 시각 없으면 되묻기 · 부정문 차단 · 허용 전 지원 외를 확인한다. T15는 허용됐을 때만 규칙 후보가 되어(`OPT_IN`) 허용 전에는 충돌 규칙으로 기존 행동을 지우지 않는다.
- AI-D15와의 관계: 조건 목록(`conditions.py`)은 건드리지 않았다. 시각 표시는 날짜 계산 코드(코드 칸)가 원래 글자를 기록하는 것이고, 모델 판단을 덮어쓰지 않는다.
- 대안: backend가 `due_raw` 글자에서 시각을 다시 찾기 — 같은 날짜 해석 코드가 두 곳에 생겨 기각. 시각이 없으면 하루 종일 일정으로 넣기 — 회의 시각을 사용자가 다시 넣어야 하고 자동 등록 기준(D50 결정 8 ④ 몰아서 확인)이 약해져 기각.
- 위험 · 남은 일: 회의 할 일의 기한 문구 뒤 마감 시각만 있던 메일은 회의 `due_at`이 마감 시각에서 보정값(18:00 등)으로 바뀐다(어느 쪽도 회의 시각이 아니라 `due_time_stated=false`로 표시). 시각이 기한 문구에서 10글자 넘게 떨어져 있으면('11/5(목) 3층 대회의실, 오후 2시') 시각 글자를 놓쳐 false가 된다. 이때는 자동 등록하지 않고 카드로 넘기므로 잘못 들어가지는 않는다(누락 쪽이 아니라 수동 쪽). T15가 허용된 뒤의 명령 평가는 새 세트가 필요하다(데이터 · 평가, 지금 세트는 일정 등록을 지원 외로 채점한다). backend `schemas`의 `/classify` 응답에 두 칸을 더하는 일은 BE-9 쪽에서 한다.

### AI-D21 · 오늘 요약은 세는 일은 코드, 문장은 모델이 쓰고, 무엇이 있는지만 알린다 — AI-13 v3 (2026-11-13)

  3. 건수와 묶음은 코드(`today_facts`)가 센다. 모델은 같은 업무로 보이는 쌍을 찾고 문장을 쓰는 일만 한다. 숫자 줄은 응답의 `counts`로 따로 주고, 화면은 기한 지남 · 오늘까지 · 응답 대기를 이 값으로 보인다. `counts.pending`은 '지금 남은 미처리(나중에 · 제외 빼고, 받은 날과 관계없이)'라 대시보드 1열 '미처리'(UX-D2: 미처리 + 나중에, 받은 날 기준)와 뜻이 다르다. 그래서 화면에 '미처리'로 보이지 않고 브리핑 검증에만 쓴다. 화면의 미처리 숫자는 대시보드 값 하나다(#61 리뷰).

### AI-D19 · 판단은 모두 모델이 한다 — 규칙은 구조 · 틀만, 모델 답을 바꾸지 않는다 — AI-23 (2026-11-13)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11/13) · 리뷰: [미정] · 공동: BE(분류 작업 재호출) · 근거: AI-D15(판단은 모델) · 사용자 지시 11/13("규칙은 구조, 틀의 역할이지 하나하나 세세하게 관여하지 않는다. 절대로")
- 문제: AI-D15로 "판단은 모델, 규칙은 조건만"을 정했지만, 그 뒤 결정(11/8 · 11/11 AI-D17 ①)으로 규칙이 모델 답을 바꾸는 곳이 8군데 생겼다. 바뀐 40통에서 규칙이 모델의 메일 성격을 바꾼 메일이 7통(참조 4 · 공지 3)이었고, 모델 호출이 실패한 2통은 규칙이 만든 결과가 정답으로 채점됐다. backend는 호출 실패 메일의 규칙 결과를 '완료'로 저장하고 자동으로 다시 부르지 않았고, 자동 발송 주소(noreply 등) 메일은 모델에 보내지도 않았다. 명령 해석은 규칙이 먼저 행동을 정하고 모델은 규칙이 못 정한 문장만 받았다.
- 결정: 모델 답을 바꾸던 규칙을 모두 뺀다(대체: AI-D17 ①, 11/8 참조 · 자동 발송 조건, AI-D15 예외 2개, D44 · D55의 '명령 해석은 규칙 + 예시 우선').

  | 3 | '필요 없다' 문장을 정규식으로 찾아 모델 할 일을 옮김 | 모델이 정한다(정의 그대로) |

  | 10 | (명령) 규칙이 행동을 정하고 모델은 남은 문장만 | 모든 지시를 모델이 먼저 읽고 행동을 고른다(`agent_v1.3`) |

- 결정(규칙에 남는 일 — 구조 · 틀): 사실 읽기(받는 방식 · 배포 목록 종류 · 사내외 · 자동 발송)를 모델 입력에 적기, 기한 날짜 계산, 메일에 없는 기한 걸러내기, 근거 문장, 우선순위 공식, 칸 배치, 5분류 묶음, 명령의 허용 목록 검증 · 날짜 계산 · 빠진 값 되묻기. 모두 모델 답을 다른 답으로 바꾸지 않는다.
- 결정(남긴 안전장치 3개 — 모델 답을 바꾸지 않고 사람에게 넘기거나 실행하지 않음):

- 결정(실패 처리, backend): ai `/classify` · `/agent/plan`은 모델이 판단하지 못하면 규칙 결과 대신 이유를 돌려준다. quota(하루 한도 소진, 503)는 시도로 세지 않고 대기열에 남기며 작업자가 10분(`CLASSIFY_QUOTA_WAIT`)씩 쉬며 다시 본다. auth(키 없음 · 401 키 거절, 503)도 설정 문제라 시도로 세지 않고 quota처럼 기다린다(11-14 #67 리뷰: 키 없는 환경에서 받은 메일이 모두 failed가 되던 것). model_failed(503) · bad_output(502)은 시도로 세며 다시 부르고 3번이면 failed(사람이 다시 시도). 예전에 저장된 규칙 결과는 기존 `retry(rule_only=True)`로 바꿀 수 있다.

- 문제: 리마인더의 '내가 한 약속 · 상대 약속 지남 · 기한 바뀜 · 끝난 것 같아요 · 끊긴 대화'는 받은 메일의 업무가 아니라 메일 속 한 줄에서 나온다. 내가 보낸 메일의 "금요일까지 드리겠습니다", 상대 답장의 "내일 오전까지 보내 드릴게요", 같은 대화의 "마감이 11/20으로 미뤄졌습니다", "제가 이미 처리했으니 안 하셔도 됩니다" 같은 문장이다. 지금 ai에는 이것을 읽는 곳이 없다.
- 결정(엔드포인트를 따로 둔다): `POST /signals`를 새로 두고 `/classify`는 손대지 않는다. 분류 프롬프트(`classify_v8`)에 신호를 더하면 할 일 판단이 흔들릴 수 있고, 그러면 40통 · core50 측정을 처음부터 다시 해야 한다. 또 분류는 받은 메일만 보지만 내 약속은 보낸 메일에서 나오므로, 보낸 메일에도 부를 수 있는 길이 따로 필요하다. backend는 분류가 끝난 받은 메일과 보낸 메일 동기화 때 부르고, 대화에 미처리 업무가 없는 받은 메일은 부르지 않아 호출 수를 줄인다.
- 결정(모델이 판단하는 것): 약속인지, 누가 했는지(me · them), 무엇을 하겠다는지, 기한 문구, 미처리 업무의 기한이 바뀌었는지와 새 기한 문구, 업무가 끝났는지와 이유(다른 사람이 처리 · 취소 · 필요 없어짐), 받은 메일이 나에게 답을 바라는지. 프롬프트 `signals_v1`에 정의와 예시 4통을 두었다. 받는 사람의 필요에 건 제안("필요하시면 보내 드리겠습니다"), 이미 한 일, 일을 해 달라는 부탁만 있는 메일은 약속 · 질문이 아니라고 정의로 적었다. 일어날지 모르는 일에 건 말("추가 요청이 생기면 연락드리겠습니다")도 약속이 아니고, 정해진 일이 끝나면 하겠다는 말("설치가 끝나는 대로 공유드릴게요")은 약속이다(11-14 검수).
- 결정(코드가 지키는 형식 — 모델 답을 다른 답으로 바꾸지 않고, 맞지 않는 신호만 버린다):
  1. 근거는 이 메일 본문 문장에 글자 그대로 있어야 한다. 공백만 느슨하게 맞추고 본문 문장 그대로 돌려준다(AI-D14 형식). 앞 메일 · 제목 · 서명 아래 글자는 근거가 아니다. 근거가 없으면 지어낸 신호일 수 있어 버린다. 근거를 모델이 고친 문장으로 두면 화면 형광펜이 칠할 곳을 찾지 못한다.
  2. 날짜는 메일 보낸 시각을 기준으로 `pipeline/dates.py`가 계산한다. 마감 표지가 붙은 문구는 `parse_deadline`, 날짜만 있는 문구('11/20 · 내일 오전')는 그 날짜로 읽는다. '다음 주'처럼 날짜를 정할 수 없으면 날짜는 비우고 문구는 남긴다. 메일에 근거가 없는 기한 문구는 지어낸 것으로 보고 약속에서는 기한만 지우고, 기한 변경은 새 기한이 핵심이라 신호를 버린다.
  3. 업무 번호(`task_id`)는 backend가 보낸 미처리 업무 안의 것만 받는다. 새 기한이 지금 기한과 같으면 바뀐 것이 아니므로 버린다.
  4. 보낸 메일의 약속은 me, 받은 메일의 약속은 them만 받는다. 쓴 사람이 정해져 있으므로 방향과 다른 who는 누가 약속했는지 틀린 신호다. 보낸 메일은 내가 쓴 것이라 '나에게 온 질문'을 늘 false로 둔다.
- 결정(실패 처리): 모델이 판단하지 못하면 규칙으로 신호를 만들지 않는다(AI-D19). 다만 `/classify`처럼 503 · 502로 실패를 알리지 않고, 200으로 신호 없이 돌려주며 `source: "none"`과 `fallback`에 이유를 적는다(`quota` · `model_failed` · `bad_output` · `empty_body`). 신호는 분류를 보탤 뿐이라 이 호출이 실패해도 메일 처리 자체가 막히면 안 되고, 문맥 기억(`/memory/extract`)과 같은 방식이 backend에 단순하기 때문이다. backend는 fallback을 보고 분류와 같은 규칙으로 다시 부른다. quota는 시도로 세지 않고 한도가 풀린 뒤, model_failed · bad_output은 시도로 세며 다시 부르고, empty_body는 다시 부르지 않는다. JSON이 아닌 답은 호출부가 model_failed로 올리고, JSON이지만 네 칸의 틀이 맞지 않으면 bad_output이다.

- 경계 사례 점검(11-14, 가짜 모델로만 확인했고 실제 모델은 부르지 않았다): 근거 확인에서 형식 규칙이 너무 느슨하거나 너무 엄격했던 다섯 곳을 고쳤다. 모델이 내는 판단은 그대로이고, 버리는 기준만 바로잡았다.
  1. 답장 아래에 붙은 앞 메일(인용)을 이 메일의 글로 보던 문제를 고쳤다. 지금까지는 '-----' 구분선만 인용의 시작으로 보았다. 그래서 Outlook 답장의 밑줄 구분선과 '보낸 사람: · From:' 머리글, Gmail의 '~님이 작성: · ~ wrote:' 줄과 '>' 인용 아래에 있는 내 예전 약속을 모델이 근거로 내면, 코드가 그대로 받아 상대 약속으로 저장될 수 있었다. 이제 이런 줄부터 아래는 근거로 받지 않는다. 받은 메일 4가지 인용 형식 모두에서 그런 신호가 버려지는 것을 확인했다.
  2. 본문이 서명이나 인용뿐이라 이 메일이 쓴 문장이 하나도 없으면 모델을 부르지 않고 `empty_body`로 돌려준다. 근거로 삼을 문장이 없으면 어떤 신호도 남을 수 없어서, 그런 메일에 하루 한도를 쓰지 않기 위해서다. 그동안은 본문이 공백뿐일 때만 그렇게 했다.
  3. 본문에 폭 없는 공백(U+200B)이나 BOM이 섞여 있거나, 전각 괄호처럼 넓은 글자를 쓰거나, 맥 메일처럼 한글을 풀어 쓴(NFD) 경우에는 모델이 같은 문장을 옮겨도 근거를 못 찾아 신호를 버렸다. 이제 비교할 때만 이런 글자를 보통 글자로 맞추고, 돌려주는 근거는 여전히 본문 문장 그대로다.
  4. 모델이 떨어진 두 문장(첫째 · 셋째 문장)을 줄바꿈으로 이어 근거로 내면 통째로 찾지 못해 버렸다. 이제 줄마다 본문 문장을 찾고, 모든 줄을 찾았을 때만 그 문장들을 본문 순서로 돌려준다. 한 줄이라도 본문에 없으면 지금처럼 버린다.
  - 개발 세트 39통은 이 변경으로 본문 문장이 하나도 바뀌지 않았다(인용 · 특수 글자가 든 메일이 없다). 그래서 위 측정 표의 정답 수와 라벨 점검 결과는 그대로다.
  5. 기한 문구 근거 확인(`_grounded`)도 근거 문장처럼 이 메일이 쓴 부분(제목 + 인용 · 서명 위)에서만 찾는다. 그동안은 인용을 포함한 본문 전체와 비교해, 앞 메일에만 있는 기한 문구가 이 메일 약속의 기한으로 붙을 수 있었다(#83 리뷰).
  - backend(BE-12)가 근거를 다시 확인할 때는 근거 전체를 한 덩어리로 본문에서 찾는다. 4번처럼 떨어진 문장을 이은 근거는 줄 사이에 다른 문장이 있어 ai에서는 통과해도 backend에서 버려진다. backend도 근거를 줄마다 찾도록 맞춰야 한다 `[BE-12에 전달]`. 3번은 ai가 본문 문장을 그대로 돌려주므로 backend에서도 통과한다.

### AI-D24 · 출력 상한 16,384, 캐치봇은 초안을 만들지 않는다, 명령 해석은 정확도만 본다 (2026-11-17)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-17) · 리뷰: [미정] · 근거: PR #195 · PR #200(AI-D22)(최수호, dev9 강도 · 시간 제한 측정) · docs.exaone.ai/ko/docs/k-exaone-2.5
- 원칙: **늦어도 정확하게.** 메일에서 지시한 업무를 틀리는 것은 허용하지 않는다. 처리 시간은 기록만 하고 합격 기준으로 쓰지 않는다(명령 해석의 '응답 시간 기준'도 두지 않는다).
- 결정:
  1. API 출력 상한 `API_MAX_TOKENS` 4096 → 16,384(4배). 추론 토큰도 상한에 들어가 긴 메일이 추론만 하다 빈 답(`finish=length`)으로 끝났다(dev9 max 실패 5회 모두). 문서 한계는 입력 + 상한 ≤ 524,288. 상한은 최대값이라 짧은 답은 늘지 않는다.
  2. 같은 날 AI-D22(PR #200)의 '출력 상한 4096 유지(120초 제한에서는 시간이 먼저 걸린다)'를 바꾼다. 정확도 우선 원칙에 따라 백그라운드 호출은 제한 시간도 함께 늘리는 쪽으로 간다(AI-28). 인용 메일 서명 자르기(`trim_body`)는 PR #200이 고친다.
  3. 캐치봇은 초안을 만들지 않는다(T07 · T12 → 메일 답장 칸 [다듬기] 안내). 행동은 목록에 남겨 모델이 알아듣고 안내하게 한다.
- 남은 일: 분류 강도는 상한을 올린 상태로 최수호가 강도별 · 본문 길이 구간별로 다시 잰다(`io_spec.md` 4.1 · 6절). 길이 구간마다 다른 강도가 반복해서 뚜렷하게 나을 때만 나눈다.
