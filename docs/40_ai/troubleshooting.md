## AI-T4 · 서버에서 7.8B를 띄우자 VS Code 원격 연결까지 끊김 (2026-11-02)

- 증상: llama-server로 EXAONE 3.5 7.8B Q4_K_M을 올리자 서버가 멈추고 VS Code Remote · SSH 연결이 끊겼다.
- 원인: user41 메모리 한도(`memory.high` 5 GiB, 스왑 없음)에 모델 4.5 GB와 VS Code 서버 · 확장 약 2.5 GB가 함께 올라갔다. 모델 파일 캐시가 계속 밀려나고 /home 디스크가 100%라 다시 읽기도 느렸다.
- 해결: 서버 7.8B를 내리고 2.4B로 임시 운영했다. 2.4B는 벤치 v2(11통, 조건 C)에서 할 일 여부 91% · 마감 73%로 7.8B(100% · 91%)보다 낮고 교육 이수 공지 1통을 놓쳤다. 엑사원을 PC에서 돌리고 서버는 터널로 부르도록 바꿨다(AI-D9).

## AI-T5 · 엑사원이 할 일 없는 회신 · 완료 보고에 '확인' 할 일을 만듦 (2026-11-03)

- 상태: 일부 해결 · 발견: 문규남 · 해결: 문규남(11/3, v3) · 리뷰: [미정] · 공동: 데이터 · 평가 · 근거: plan 4.2 · 4.3 · 4.4절
- 증상: 라우터가 엑사원으로 보낸 메일 중 할 일이 없는 메일에 '~ 확인' 할 일을 만들었다. 대부분 마감이 없다. 예: 'RE: [요청] 개발 서버 증설'(내 요청에 대한 완료 회신) → '증설 작업 검토', '[보고] 개발계 백업 주기 변경 완료' → '변경 완료 확인'. dev 7건 · test 5건. Task 정밀도가 dev 98.4%(규칙만 v1) → 88.2%(엑사원 v1), test 87.0%(규칙만 v1) → 78.9%(엑사원 v1)로 떨어졌다.
- 원인: 모델이 '읽고 확인'과 '해야 할 일'을 잘 가르지 못한다. 프롬프트 예시를 늘린 v2에서도 공지 · 사외 행사 · 참조 · 회신에 할 일을 만들었다(dev 엑사원 경로 19통 중 13통 오답). 긴급 · 지목도 거의 늘 true로 냈다.
- 해결: ① 완료 · 확정 회신은 규칙으로 판별(mail_rules_v1.2) ② 공지의 '미이수자는 · 해당자는' 당부는 엑사원에 묻지 않음(v1.3) ③ 합치기 규칙(`classify._from_model`): 긴급 · 지목은 규칙 값, 사외 메일의 공지 · 참조는 기타, 회신 · 참조 · 기타를 맨 앞에 둔 모델 할 일은 규칙도 요청을 못 찾았을 때 제외, 같은 당부를 쪼갠 기한 없는 '결과 검토' 제거. 누락 방지(D15, 규칙 할 일 유지)는 그대로. 결과 Task 정밀도(→ 뒤는 모두 v3): dev 92.3%(엑사원 v2) → 98.4%, dev2 81.8%(v2 프롬프트 + 이전 합치기) → 87.1%, test 78.9%(엑사원 v1) → 91.2%, 누락은 셋 다 0. 비교 기준 버전이 세트마다 다르다 — test는 테스트셋을 한 번만 재는 원칙 때문에 v2를 재지 않아 v1과 비교했다(plan 4.3 · 4.4절).
- 남은 것: test 정밀도 91.2%로 목표 95% 미달. 지목 없는 전사 공지('10/21까지 업데이트해 주시기 바랍니다')는 D15 때문에 엑사원으로 보내고, 모델이 할 일을 만든다. 마감 없는 '~ 확인' 할 일을 일괄로 지우는 방안은 누락 위험 때문에 넣지 않았다.
- 재발 방지: 엑사원 경로 수정 뒤에는 Task 정밀도도 함께 본다(누락 0만 보면 놓친다). dev만이 아니라 보조 개발셋 dev2로도 잰다(`run_dummy.py --set dev2`). 합치기 실험은 모델을 다시 부르지 않고 `--replay`로 한다.

## AI-T6 · 지원하지 않는 '메일 다 지워줘'를 제외 처리(T10)로 해석 (2026-11-03)

- 상태: 해결(v1 26문장 기준) · v4 엑사원 포함 재측정 필요 · 발견: 문규남 · 해결: 문규남(11/3) · 리뷰: [미정] · 공동: 데이터 · 평가 · 근거: plan 4.2 · 4.4 · 4.6절 · detail 4절
- 증상: 명령 테스트 C-024 '메일 다 지워줘'(기대: 지원 외 → 행동 없음)를 엑사원이 T10 제외 처리로 바꿨다. C-026 '보고서 건 정리 좀'(애매 → 되묻기)은 T01 오늘 요약으로 해석했다.
- 원인: 모델 경로가 허용 목록 안의 가장 가까운 행동을 고른다. '지원 외 · 모르겠음'을 고르는 예시가 부족했다.
- 해결: 삭제 · 지우기는 규칙에서 지원 외(agent_rules_v1.1), 모델은 애매하면 ambiguous(agent_v1.1). agent_rules_v1.2에서 행동이 0개 걸린 지시 중 메일 조작(전달 · 차단 · 첨부 저장 등) · 메일 무관 요청은 지원 외, 대상 없는 '알아서 · 정리 좀'은 되묻기로 규칙이 끝낸다(엉뚱한 행동 실행으로는 가지 않는다). 엑사원 포함 26/26, 모델로 가는 문장 3 → 1개.
- 11-14(AI-23 · AI-D19): 모든 지시를 모델이 먼저 읽게 바꾸면서 이 규칙 검사가 명령 경로에서 빠졌다(#67 리뷰에서 발견). 모델이 고른 상태 변경 행동에도 같은 검사를 다시 걸어 지원 외로 끝낸다(AI-D19 안전장치 3). 재현 테스트 4개(`test_unsupported_wins_over_model_state_change`).
- 남은 것: 26문장 세트(v1)는 규칙 작성자가 만들었고 C-024 · C-026 오답을 보고 규칙을 고쳤으므로 26/26은 개발 세트 점수에 가깝다. 독립 출제 세트 v4(100문장)는 규칙만 v1.4가 73/100(위험한 오탐 1)이고, 엑사원 포함은 v1.3에서 60/100 · 위험한 오탐 10이었다. v1.4 엑사원 포함 채점은 아직 없다(plan 4.6절) — v4 · 봉인 v3로 한 번씩 잰 뒤 상태를 다시 정한다.
- 재발 방지: 규칙 확대는 평가 문장이 아닌 새 문장으로 테스트한다(ai/tests/test_agent.py). 새 거절 정규식은 backend 허용 목록을 보지 않으므로, '전달' 같은 행동이 레지스트리에 생기면 정규식에서 그 낱말을 뺀다.

## AI-T7 · 엑사원 응답이 메일 1통 35초 · 명령 해석 22초로 느림 (2026-11-03)

- 상태: 일부 해결 · 발견: 문규남 · 해결: 문규남(11/3, v3) · 리뷰: [미정] · 공동: — · 근거: plan 4.4절 · detail 8절 #6
- 증상: PC 엑사원으로 메일 분류 1통 평균 35.3초, 명령 해석 모델 경로 21.8초, 첫 호출 57~117초. 한 번은 첫 메일이 제한 시간 120초에 걸렸다.
- 원인: ollama 응답의 시간 칸을 기록해 나눴다. 분류 1통 = 입력 읽기 16.8초(48%) + 출력 생성 18.4초(52%), 로딩 0초. 새 입력은 초당 약 12~18토큰, 출력은 초당 약 3.3~4토큰(CPU만, `num_thread`를 바꿔도 빨라지지 않음) → 토큰당 속도는 PC 한계다. 시스템 프롬프트(약 950토큰)는 프리픽스 캐시가 맞으면 1초 안, 안 맞으면 80초다. 명령 해석 22초 · 첫 호출 117초는 대부분 캐시 미적중이었다(캐시가 맞은 명령 해석은 약 4초).
- 해결: 방식 쪽 토큰을 줄였다. 분류 프롬프트 v3(출력 칸 3개 제외 · 서명란 한 줄)로 입력 1130 → 925토큰, 출력 61 → 45토큰, 1통 35.3 → 21.5초(test 21.7초). 서비스 시작 때 분류 시스템 프롬프트까지 미리 읽혀(warm) 첫 메일 캐시 미적중을 없앴다. 규칙 경로를 넓혀 엑사원 호출을 dev 19 → 17통, 명령 26개 중 3 → 1개로 줄였다.
- 남은 것: 1통 20초대 아래로는 CPU에서 어렵다. GPU 서빙은 미결 #6으로 팀이 정한다. PC ollama를 다시 띄우면 첫 호출은 다시 캐시 미적중이다.
- 재발 방지: `run_dummy.py --llm` 보고서의 '엑사원 호출' 절에서 입력 · 출력 토큰과 초를 함께 본다. 프롬프트를 늘릴 때는 메일마다 바뀌는 값을 시스템 프롬프트에 넣지 않는다(캐시가 깨진다).

## AI-T8 · 분류 · 명령 시스템 프롬프트 캐시가 서로 밀어내 첫 호출이 70~120초 (2026-11-03)

- 상태: 일부 해결 · 발견: 문규남 · 해결: 문규남(11/3, 채점 실행기) · 리뷰: [미정] · 공동: — · 근거: plan 4.4 · 4.5절
- 증상: dev2 채점의 첫 메일(M-0001)이 두 번 120초 제한에 걸려 규칙 결과로 떨어졌다. 분류 채점 바로 뒤 명령 해석 모델 경로 1건이 70.6초였다(캐시가 맞으면 약 2~4초).
- 원인: PC ollama는 프리픽스 캐시 칸이 하나라, 다른 시스템 프롬프트(분류 v3 · v4, 명령)를 부르면 앞의 캐시가 밀려난다. 밀려난 뒤 첫 호출은 시스템 프롬프트를 처음부터 읽는다(분류 약 90초, 명령 857토큰 약 68초). 채점 실행기는 ai 서비스와 달리 시작 때 미리 읽기를 하지 않았다. plan 4.4절의 '분류 · 명령을 번갈아 불러도 캐시는 유지됐다'는 이번 측정과 다르다.
- 해결: 채점 실행기도 시작 전에 분류 시스템 프롬프트를 미리 읽히고, 걸린 시간을 보고서 머리에 따로 적는다(`run_dummy.py`). 이후 dev2 · 테스트셋 호출 실패 0건.
- 남은 것: ai 서비스에서 분류와 명령을 섞어 부르면 같은 일이 생긴다. PC ollama `OLLAMA_NUM_PARALLEL=2`로 캐시 칸을 둘로 두고 두 프롬프트를 모두 미리 읽히는 안을 실측으로 확인한다(메모리 약 1GB 추가 `[추정]`).
- 재발 방지: 보고서의 '첫 호출' · '호출 실패' 칸과 `_fallback`을 본다. 같은 PC에서 다른 프롬프트를 시험한 뒤에는 미리 읽기 시간이 90초 안팎으로 다시 늘어난다.

## AI-T9 · 같은 프롬프트인데 PC 출력 속도가 초당 4.0 → 2.6토큰으로 떨어짐 (2026-11-03)
