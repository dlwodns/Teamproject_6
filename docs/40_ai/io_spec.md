## 2. 호출별 입력 · 출력

### 공통

| 항목 | 값 |
|---|---|
| 주소 · 형식 | `https://api.exaone.ai/v1/chat/completions`, OpenAI 호환, JSON 스키마 강제(거절되면 강제 없이) |
| 추론 | 끌 수 없음. 강도 `low` · `high` · `max`(기본 max). 추론 토큰도 출력 상한에 들어간다 |
| 상한 한계 | 입력 + `max_tokens` ≤ 524,288 (docs.exaone.ai/ko/docs/k-exaone-2.5) |
| 샘플링 | 지금 `temperature` 0. 문서 권장 1.0 · `top_p` 0.95는 측정 후보 |
| 개인정보 | backend가 이름 · 주소 · 전화를 가려 보내고 되돌린다. 가림이 판단을 바꾸지 않음(dev4 40통, PR #195) |
| 실패 | 하루 한도 → 다시 부르지 않음. 429 · 5xx → 3회 재시도. 응답의 `source` · `fallback`으로 알린다 |

### 2.1 A1 메일 분류 `/classify` (`ai/app/schemas/classify.py`)

| 받는 것 | 주는 것 |
|---|---|
| `mail_id` · `from` · `to[]` · `cc[]` · `subject` · `body`(가린 본문) · `attachments[]` · `received_at` | `category`(요청 · 회신 · 공유 · 공지 · 기타) · `action_types[]` |
| `owner{email, name, position, team, member_of[], role_lists[], team_lists[]}` | `tasks[]{type, text, format, due_raw, due_at, due_time_stated, end_at, evidence, deliver_to}` |
| `sender{is_superior, is_favorite}` | `checks[]{text, reason, evidence}` · `lane`(할 일 · 확인 · 참고) · `mentioned_me` · `urgent` · `is_follow_up` · `priority` |
| | `source` · `model` · `prompt_version` · `rules_version` · `fallback` |

모델이 정함: 할 일 여부 · 유형 · 문구 · 기한 표현 · 보낼 곳 · 메일 성격. 코드가 정함: 기한 날짜 · 근거 문장 확인 · 우선순위 · 칸. 실패하면 503 → backend가 다시 부른다.

### 2.2 A2 명령 해석 `/agent/plan` (`ai/app/schemas/agent.py`)

| 받는 것 | 주는 것 |
|---|---|
| `text` · `actions[]{id, name, description}`(backend 레지스트리) · `context{now, selected_mail_ids[], last_result_ids[]}` | `action`(T01~T17 또는 null) · `target{sender, category, date_range, keyword, mail_ids[], awaiting_reply}` · `params{}` · `reason`(unsupported · ambiguous) |

메일 본문은 넣지 않는다. 합격 기준은 **정확도만** 본다(응답 시간은 기록만, 11-17). 정확도 기준값은 5절 #6.

### 2.3 A3 리마인더 신호 `/signals` (`ai/app/schemas/signals.py`)

| 받는 것 | 주는 것 |
|---|---|
| `mail{direction, sender, recipients[], cc[], subject, body, sent_at}` · `me{email, name}` · `thread[]`(최근 5통, 앞 400자) · `open_tasks[]{task_id, text, due_at}` | `commitments[]{who, text, due_raw, due_at, evidence}` · `due_changes[]{task_id, new_due_raw, new_due_at, evidence}` · `resolved[]{task_id, reason, evidence}` · `asks_me_question` · `fallback` |

### 2.4 A4 발신자 정보 추출 `/memory/extract` (`ai/app/schemas/memory.py`)

| 받는 것 | 주는 것 |
|---|---|
| `mail_id` · `from` · `sender_name` · `subject` · `body`(가린 본문) · `owner{email, name, position, team}` | `facts[]{kind(works_on 맡은 일 · org 소속), value, evidence}` · `source` · `fallback` |

근거 문장이 본문에 글자 그대로 없으면 버린다. 사적인 사실은 뽑지 않는다. '메일 내용 분석 허용'을 켰을 때만 부른다.

### 2.9 A9 사람 조회 — 행동 T17 `사람_조회` (11-17 결정 · 구현)

**하는 일**: "장민호 차장이 누구였지? 어떤 메일 보냈었어"처럼 물으면 그 사람이 누구인지와 보낸 메일 · 업무를 답한다.

**동의**: 설정의 '메일 내용 분석 허용' 켜기 · 끄기만 있다. 켜기 = 메일에서 알아낸 정보를 저장하고 **그 정보로 대화에 답하는 것**에 동의. 저장 목록을 보여 주는 화면은 두지 않는다(`reminders.md` 12.7 덧붙임).

## 3. 업무 요약 · 회고 설계 (A6)

### 3.1 공통 원칙

1. **목록 · 건수 · 순서는 코드**가 만든다(backend `reminders/briefings.py`). 틀릴 수 없는 부분이다.
2. **모델은 맨 위 '머리 문장' 최대 3개만** 쓴다. 머리 문장 = 목록을 다 읽지 않아도 오늘(이번 주)의 모양이 잡히게 하는 요약 문장이다. 예(AI-D21 실측 문장): "기한이 지난 상급자 업무는 정태성 담당의 2단계 일정 리스크 보고이며, 그 밖의 기한 지난 업무는 7건입니다."
3. 무엇이 있는지만 알린다. "~부터 하세요" 같은 권유는 쓰지 않는다(AI-D21).
4. 모델 문장은 코드가 검사한다(길이 · 권유 표현 · 입력에 없는 숫자 · 건수 · 이름+직책). 걸리면 같은 틀의 코드 문장을 쓴다.
5. 정한 시각에 미리 만들어 둔다. 화면 · 대화(T01)는 저장본을 읽는다(모델 1회 수 분, AI-D21).

- 근거: Todoist '오늘' 보기는 기한 지남을 맨 위에 따로 두고, 그 아래를 시각순으로 둔다(todoist.com/help/articles/360006365600). 업무 요청(유형)별 묶음은 대시보드 2열(회신 · 요청 · 검토 · 기타)과 같은 모양이라 새 정보가 적다.
- **시각 없는 오늘 마감의 위치**: Todoist는 '종일' 항목을 시각 있는 항목보다 **앞**에 둔다. 맨 뒤에 두면 놓칠 수 있어 2번(기한 경과 바로 아래)을 제안한다. 근거는 Todoist 하나라 약하다.

### 3.4 주간 업무 회고 (금 17:30) — 제안

**주간 회고란**: 한 주를 닫고 다음 주를 여는 정리다. 널리 쓰이는 방식은 셋 다 같은 세 축으로 모인다 — **[이번 주에 끝낸 것] · [남은 것 · 막힌 것 · 남이 쥐고 있는 것] · [다음 주에 다가오는 것]**.

| 출처 | 구성 |
|---|---|
| GTD 주간 리뷰(David Allen) | 지난 일정 · 다가올 일정 · 기다리는 목록(Waiting For) · 할 일 목록 확인 (gettingthingsdone.com/2009/05/the-gtd-weekly-review) |
| PPP 보고 | Progress(끝낸 것) · Plans(다음 기간) · Problems(막힌 것) |
| 한국 주간업무보고 | 금주 실적 · 차주 계획 · 이슈 · 협조 사항 (근거: 블로그 · 서식 사이트뿐, 약함) |
| Sunsama 주간 리뷰 | 한 일(요일별) · 완료 요약(공유용) (help.sunsama.com/docs/weekly-review) |

**제안 구성(4묶음, 모두 코드로 셀 수 있음)**

| 묶음 | 조건 | 근거 |
|---|---|---|
| 1. 금주 완료 업무 | 이번 주 월 00:00 ~ 회고 시각에 완료. 요청자별로 묶고 상급자 먼저. **기한 뒤에 끝낸 것은 줄에 '기한 후 완료' 표시 + 건수**만 | PPP Progress · 금주 실적 |
| 2. 다음 주로 넘어가는 일 | 미처리이면서 기한이 지났거나, 이번 주에 연기했는데 아직 미처리 | PPP Problems · 주간보고 이슈 |
| 3. 회신 대기 | 내가 보낸 요청 중 답을 기다리는 것 · 상대의 약속. 오래된 순 | GTD Waiting For |
| 4. 차주 마감 업무 | 미처리이면서 기한이 다음 주 월~금. 날짜순 | PPP Plans · 차주 계획 · GTD 다가올 일정 |

- 지금과 다른 점: 지금은 '금주 완료 · 기한 경과 후 완료 · 회신 대기' 셋이다. **'기한 경과 후 완료'를 따로 묶지 않고 1번 안의 표시로 옮기고, 2번 · 4번을 더한다.**
- 넣지 않는 것: 점수 · 목표 대비 진행(Todoist Karma) — '있는 것만 말한다'와 충돌. 시간 사용 분석 — 기록 데이터가 없다. 제외 처리한 목록.
- 머리 문장 3개(제안): ① 이번 주 완료 건수 + 기한 후 완료 건수 ② 다음 주로 넘어가는 일 건수 + 상급자 건 이름 ③ 다음 주 기한 건수 + 가장 몰린 요일
- 모델 문장이 꼭 필요한지는 일일 두 종류를 재 본 뒤 정한다(건수 위주라 코드 문장으로 충분할 수 있다).

### 3.5 입출력 · 강도 (세 종류 공통)

## 4. 강도 · 출력 상한 정하기

### 4.1 분류 강도 — PR #195 결과(최수호, 11-16, 가린 본문 · `classify_v8`)

dev9 20통(긴 메일 포함) · 제한 시간 10분 · 상한 4096:

**정하는 순서(11-17 결정)**: ① 출력 상한을 올린다 → ② 강도별로 다시 잰다 → ③ 본문 길이 구간별 점수를 본다 → 구간마다 가장 좋은 강도가 **반복해서 · 뚜렷하게** 다르면 그때만 길이에 따라 나눈다. 아니면 하나로 고정. 측정은 최수호(요청문 6절).

### 4.2 출력 상한

- 11-17 **16,384(4096의 4배)**로 올렸다(결정: 문규남). 문서 한계(입력 + 상한 ≤ 524,288) 안이다. 상한은 최대값이라 짧은 답의 토큰을 늘리지 않는다.
- 주의: 상한을 올리면 긴 메일에서 추론이 더 길어질 수 있어 처리 시간이 는다. 백그라운드 호출(A1 · A3 · A4 · A6)은 제한 시간을 함께 늘린다. 사용자가 기다리는 A2 · A5도 정확도 우선 원칙에 따라 늘릴 수 있지만 backend 대기(130초)를 함께 고쳐야 한다.
- 코드: `ai/app/llm/client.py` `API_MAX_TOKENS` = 16384(모든 호출 공통). 평가 실행기(`run_dummy.py --llm`)도 같은 호출부라 그대로 적용된다.
