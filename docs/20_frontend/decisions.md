## 1. 결정

### UX-D1 · 대시보드는 '업무'와 '확인사항'을 나눠 보여 준다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(UX/UI, 11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 공동: — · 근거: D40 · AI-D10(`lane`) · `ai/app/pipeline/checks.py`
- 결정: 업무(lane=할 일)는 2열 칸에, 업무가 아닌 메일은 1열 '확인사항' 카드에 둔다. 카드 탭은 `확인`(완료 보고 · 결과 회신 · 해당 여부 확인 · 시스템 알림 · 읽고 확인)과 `참고`(일반 공지 · 공유 · 뉴스)이고 기본은 확인 탭이다. 기본 3건, 나머지는 더보기로 오른쪽 사이드바(UX-D12). 이름은 처음 '알아둘 정보'였다가 UX-D11에서 '확인사항'으로 바꿨다.
- 근거: 확인 · 참고 메일은 업무로 세면 정밀도가 떨어지고(AI-T5), 버리면 정보를 잃는다. 사용자는 공지처럼 알아야 할 정보도 대시보드에서 보길 원했다.
- 바뀐 것: D40 "공지 · 참조는 메일 화면에서 분류로만 보인다" → 대시보드 '확인사항'에도 보인다. 업무를 만들지 않는다는 결정은 그대로다.

### UX-D2 · 1열은 받은 날 기준 업무 수(건수만)다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D20-1 · D20-4
- 결정: 1열 맨 위 카드는 **메일을 받은 날** 기준으로 들어온 업무의 전체 · 처리 · 미처리 건수만 보인다. 기간은 오늘 · 이번 주 · 날짜(하루 고르기). 미처리 = 미처리 + 나중에, 제외는 세지 않는다. 그 아래에 '응답 대기'(F10)와 '확인사항'(UX-D1)을 둔다 `[제안]`.
- 바뀐 것: D20-1 요약 줄 · 원형 진행률, D20-4 1열 우선 확인(기한 · 상급자 · 즐겨찾기) 칸을 없앤다. 기한 관련은 2열 긴급(UX-D3)으로, 상급자 · 즐겨찾기는 줄 표시와 정렬(D9 가중치)로 옮긴다.
- 대안: 기한 날 기준 — 기한 없는 업무가 빠져서 택하지 않았다.

### UX-D3 · 2열은 긴급 + 업무 유형 4칸이다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D39 · D40 · AI-D11(ASAP 문구)
- 결정: 2열 맨 위 '긴급' 칸 = 미처리 중 기한 지남 · ASAP(즉시) · 오늘 마감. 아래 유형 칸 = 회신 · 요청 · 검토 · 기타(공지는 업무를 만들지 않아 칸 없음). 긴급 업무도 유형 칸에 같이 보인다(중복 허용). 칸 머리 숫자는 긴급이 아닌 업무만 센다(UX-D18, 11-13).
- 결정(D40 공지 속 지목 요청, #27 리뷰): 업무 칸은 업무가 나온 메일의 분류(`category`)로 정한다. 공지 속 나를 지목한 요청은 ai가 분류를 공지가 아니라 그 요청의 분류(대부분 '요청', 회신 · 검토 요청이면 그 칸)로 낸다(`ai/app/pipeline/classify.py` `_category`, D40) → 따로 칸을 두지 않아도 해당 유형 칸에 들어간다. 분류가 '공지'인데 업무가 붙은 예외(분류 전 · 수동 분류 등)는 '기타' 칸에 둔다 — FE-D10 임시 정책(`NOTICE_TASK_POLICY = 'other'`)과 같은 방향이고, 업무 수에서는 빼지 않는다(D13).
- 바뀐 것: D20-4 2열 성격 칸(요청 · 보고 · 문의 · 공지 · 기타)과 칸 끌어서 순서 바꾸기(P0)를 없앤다. wireframe 12-5 #1('문의')은 D39로, #3(1열 칸 사이 중복)은 1열이 건수 카드가 되면서 해소됐다.

### UX-D4 · 색은 60 · 35 · 5(무채색 · 보조 4색 · LG 빨강), 서체는 Pretendard + Outfit (2026-11-07)

- 상태: 채택(방향) · 세부 값 `[제안]` · 제안: 문규남(LG CNS 브랜드 로고와 함께 쓰는 색) · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: LG CNS 사이트 CSS · 로고 SVG(`research_ux_20261107.md` 1절)
- 결정: 60% 무채색 면(#FFFFFF · #F7F8F9), 35% 보조 4색(#121212 · LG GRAY #6B6B6B · #E5E5E5 · #F0F1F3), 5% 포인트 LG Heritage Red #A50034(주 버튼 · 에이전트 버튼 · 선택 표시선 · 로고만). 상태색은 따로(위험 #B20C00 등)이고 옅은 바탕 + ⚠ + 글자로만 쓴다. 국문 제목 · 본문 · 영문 본문 Pretendard, 영문 표시 · 숫자 Outfit. 상세는 `design_system.md`.
- 바뀐 것: D21(LG RED를 '요청' 태그 · 강조 아이콘에도) → 포인트 사용처를 줄였다. FE-D7(오렌지 #FF6000 가이드, FE-1 브랜치) → 이 결정으로 대체, `frontend/src/styles/tokens.css` 교체 필요(FE-2).
- 위험: 로고 사용 허락 전에는 '로고 자리'를 둔다. LG 전용 서체(LG EI)는 외부 사용 조건 미확인이라 쓰지 않는다.

### UX-D5 · 답장은 만든다 — 하고 싶은 말만 쓰면 템플릿에 맞춰 보여 준다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D48 · wireframe 0절
- 결정: 메일 화면에서 답장을 쓴다(UX-D12로 대시보드 메일 패널은 없앰). 사용자는 보낼 내용만 쓰고, 고른 템플릿(기본 회신 · 자료 송부 · 일정 회신 · 확인했습니다)의 인사 · 맺음 · 서명 사이에 넣어 미리보기로 보여 준다. 보내기는 사용자가 누를 때만. 엑사원으로 다듬기(`/draft`)는 선택.
- 결정: 완료 확인 문구는 **"완료로 처리할까요?" · 예 / 아니오 · 체크박스 "오늘 다시 보지 않음"**.
- 바뀐 것: wireframe 0절 '만들지 않는 것'에서 답장을 뺐다. D48 문구 "완료할까요? · 오늘 하루 보지 않기"를 이 문구로 바꾼다(동작은 D48 그대로). 템플릿 자리표시자에 `{내용}` · `{발신자명}`을 더한다(BE 확인).

### UX-D6 · 답장 후 완료 확인은 아래 시트로 띄운다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D23 · D48 · M3 · NN/g bottom sheet · WAI-ARIA dialog
- 결정: 모달 아래 시트. 휴대폰은 전체 폭 + 손잡이, 840px 이상은 최대 560px로 아래에서 24px 띄운다. 아니오 · Esc · 바깥 누르기 · 쓸어내리기는 모두 '아니오'(리마인드 유지). 열리면 [예]에 포커스(되돌리기가 있으므로).

### UX-D7 · 알림 센터에 리마인더 탭을 따로 둔다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: 리마인더 R-아침 · R-기한 · R-나중에 · Outlook 리마인더 창 · Slack Later
- 결정: 🔔 알림 센터를 [리마인더 | 알림] 탭으로 나누고 리마인더를 기본으로 연다. 리마인더 줄마다 [완료] [나중에 ▾] [메일 보기]. 🔔 숫자는 리마인더만 센다. 리마인더 토스트는 자동으로 사라지지 않는다.

### UX-D8 · 에이전트는 접히는 단계 표시 + 대화 안 확인 카드 + 결과 카드로 보여 준다 (2026-11-07)

- 상태: 채택 · 제안: 문규남(스텝 인디케이터) · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D37 · Vercel AI Elements · Fluent Wait UX · NN/g · Linear · Notion(`research_ux_20261107.md` 2절)
- 결정: 단계 명령 이해 → 대상 찾기 → (확인) → 실행. 진행 중엔 한 줄("…하는 중 · n/전체 · 경과 초" + [중지]), 끝나면 "N단계 완료 · M초"로 접고, 실패하면 펼친 채 멈춘다. 확인은 모달이 아니라 대화 안 카드(동사 버튼, 대상 빼기 가능). 결과 카드는 과거형 + [실행 취소] + 해석 근거(접힘). 남은 시간은 추정하지 않고 경과 시간만 보인다.

### UX-D9 · 버튼 모핑은 네 곳에만 쓴다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: Carbon productive motion · M3 motion 토큰 · Primer loading
- 결정: 업무 체크 → 줄 빠짐, 보내기 → 보내는 중 → 보냄 ✓, ✦ 버튼 → 에이전트 패널(컨테이너 변형), 아래 시트 등장. 필터 · 탭 · 숫자 갱신에는 쓰지 않는다. 동작 줄이기 설정이면 모두 끈다. 값은 `design_system.md` 4절.

### UX-D10 · 기한 라벨은 검정 · 파랑 · 초록이고 짧게 쓴다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: UX-D4(빨강은 포인트 전용)
- 결정: 기한 지남 · ASAP = 검정 라벨(`D+2` · `ASAP`), 오늘 마감 = 파랑(`오늘 18:00`), 기한 남음 = 초록(`내일 12:00` · `11/10(화)`), 기한 없음 = 회색. ⚠ · '기한 지남' 같은 말은 라벨에 붙이지 않는다. 값은 `design_system.md` 1절.
- 근거: 빨강은 포인트(LG Heritage Red)와 대비 1.11:1이라 위험 표시에 쓰면 섞인다. 가장 급한 것을 가장 진한 색으로 두면 색이 섞이지 않고 순서가 바로 읽힌다.

### UX-D11 · 문구는 명사로 짧게, 덜어낼 수 있는 줄은 없앤다 · 메일함은 Ctrl+B로 열고 닫는다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: D20-3 · UX-D5
- 결정: 대시보드 화면 제목 · 설명 줄과 기한 지남 경고 줄(A1, '긴급 칸에서 보기')을 없앤다. 긴급 칸 설명('기한 지남 · ASAP · 오늘 마감')도 없앤다. 이름은 '업무 있는 메일' → '업무', '알아둘 정보' → '확인사항', '답장 기다리는 메일' → '응답 대기', '처리함 · 남음' → '처리 · 미처리'. 빈 상태는 '없음'. 완료 확인 시트는 제목 · 업무 목록 · 체크박스 · 버튼만.
- 결정: 메일 화면 왼쪽 메일함 = 받은편지함 · 업무 · 확인사항 / 빠른 보기(즐겨찾기 · 상급자 · 기한 지남 · 응답 대기) / 분류 / 계정. 목록 위 [▥] 버튼과 Ctrl+B(⌘B)로 열고 닫는다.
- 바뀐 것: D20-3(기한 지남 경고 줄) → 없앰. 긴급 칸과 검정 라벨이 대신한다.

### UX-D12 · 더보기는 오른쪽 사이드바, 업무를 누르면 그 메일로 간다 (2026-11-07)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #27 11-07) · 근거: UX-D1 · UX-D3
- 결정: 대시보드의 모든 더보기(긴급 · 유형 칸 · 응답 대기 · 확인사항)는 칸 안에서 펼치지 않고 오른쪽 480px 사이드바에 전부 보여 준다. 업무 줄 · 확인사항 줄 · 리마인더 [메일 보기]를 누르면 메일 화면으로 넘어가 그 메일을 고른다.
- 결정: 메일 화면 맨 위에 [← 대시보드] 버튼을 따로 두고, Alt+← / Alt+→로 이전 · 다음 화면을 오간다(입력칸 안에서는 제외). 실제 앱은 라우터 history로 만들어 브라우저 뒤로 가기와 같게 한다.
- 바뀐 것: D20-6(업무 줄 → 오른쪽 원본 메일 패널)과 wireframe 12절 `M` 패널 → 없앰. 답장 · 상태 버튼은 메일 화면에서 쓴다.

### UX-D13 · 메일 플래그는 상급자 · 즐겨찾기 · 마감 · 거래처 4종이다 (2026-11-07)

- 결정: 플래그는 **상급자 · 즐겨찾기 · 마감 · 거래처** 4종이다. 메일 화면 왼쪽 '빠른 보기'에 4종을 모두 둔다(마감 = 기한 지남 · ASAP · 오늘 마감 미처리 업무가 있는 메일 — UX-D3 긴급 칸과 같은 조건, 기존 '기한 지남'을 넓혀 대신함).

- 결정: 칩은 아이콘 + 글자(색만으로 나타내지 않음), 빨강 금지(UX-D4 포인트 전용). 값은 `design_system.md` 1절 '플래그 칩'. 칩 색은 셋 다 회색(`--c-fill` · `--c-ink`)이다 — 거래처를 정보 파랑으로 따로 둘지는 화면에서 써 본 뒤 다시 본다(11-07 문규남).

- 대안: 마감도 칩으로 — 목록 줄에서 기한 라벨과 겹쳐서 택하지 않았다.
- 우선순위(11-10 기획 리뷰): 거래처는 **P1**로 둔다. 상급자 · 즐겨찾기 · 마감은 기존 데이터로 계산할 수 있지만, 거래처는 PRD와 D9 우선순위 기준에 없던 항목이라 설정의 거래처 도메인 목록과 BE 필드를 새로 만들어야 하기 때문이다. 실제로 필요한지는 멘토링 뒤 기업 담당자에게 확인할 목록에 넣어 묻는다(홍태겸 시안 피드백 '거래처 중요 목록'과 같은 건이라 함께 묻는다, 기획 이재운). 그 전까지 시안의 거래처 칩 · 빠른 보기는 P1 화면으로 본다.

### UX-D15 · 메일 요약 — 외국어 메일의 핵심을 한국어 카드로 보여 준다 (2026-11-07)

- 상태: 채택 · 세부 `[제안]` · 제안: 문규남(과제 제시자 요구: 외국어 메일 요약 · 핵심 추출) · 결정: 문규남(11-07) · 리뷰: 이재운(기획 확인, PR #35 11-10) · 근거: Outlook 읽기 화면 제목 옆 '이 전자 메일 요약' · AI-13(`/summarize` `mode=mail`, 영문 메일 한국어 요약) · D42
- 결정: 메일 제목 옆에 **[메일 요약]** 버튼. 본문이 한국어가 아니면 버튼을 강조(채운 회색 + '외국어' 글자)한다. 누르면 본문 위에 요약 카드를 펼친다(다시 누르면 접음).
- 결정: 요약 카드 = **요지(1~2문장) · 나에게 요청한 것(목록) · 기한(원문 표현 그대로) · 원문 언어**. 카드 아래 '엑사원 요약 · 원문과 다를 수 있음'.
- 결정: 실패하면 원문을 요약처럼 보이지 않는다 → 카드 자리에 **'요약 실패 · [원문 보기] [다시 시도]'**. 코드 요약(앞 두 문장)은 본문이 한국어일 때만 요약으로 쓴다.
- 범위(11-10 기획 리뷰): **영어 메일 요약은 보장한다.** 그 밖의 언어(일본어 · 중국어 등)는 요약을 시도하되, 실패하면 위의 '요약 실패' 카드로 안내하고 원문을 보게 한다. PRD와 D42가 약속한 것은 '영문 메일 한국어 요약'이고, PRD '하지 않는 것'의 '일본어 · 중국어 번역 전문'과도 겹치지 않게 하려는 것이다(요약은 번역 전문이 아니다). PRD에도 같은 범위가 들어가 있다(PRD v3.1 11-10 보완, 기능 목록 · 하지 않는 것).
- 연결: AI 응답 형식은 AI-13 v2(`feature/AI-13-mail-summary-v2`)에서 `SummarizeResponse.mail_summary = {lang, gist, asks[], due_text}`로 맞춘다(`text`는 그대로 둠). BE에서 `/summarize` 호출은 아직 없다 → BE 후속(13-10 #9).
- 위험: 메일 본문은 엑사원에만 보내고, 엑사원이 아닌 바깥 모델로는 보내지 않는다. 엑사원을 로컬로 부를지 API로 부를지는 공통 결정을 따른다(지금은 D41, 엑사원 API 전환 PR #46이 머지되면 D52 · D53). 본문은 개인정보를 가린 값(`MailInput.body`).

### UX-D18 · 세련되게, 조작은 단순하게 — 화면 다듬기 규칙 (2026-11-13)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-13) · 리뷰: [미정] · 공동: — · 근거: Vercel Geist(배지 · 더 보기) · Atlassian(라벨) · GitHub Primer(주 버튼은 화면당 하나) · NN/g(빈 상태) · Refactoring UI · Apple Mail(안 읽음 점), 1440 · 390 폭 화면 캡처 전후 비교
- 결정(철학): 촌스럽지 않게, 디자인은 세련되게, 조작은 단순하게. 화면에 미완성 표시(점선 '로고 자리' 등)를 두지 않는다. 로고는 LG CNS 승인 전까지 'CNE' 글자만 둔다.
- 결정(빨강): 빨강 채움 버튼은 화면마다 확정하는 동작 하나에만 쓴다(답장 · 'N건 완료 처리' · 보내기). 늘 보이는 진입 단추(상단 바 에이전트)는 테두리 단추 + 빨간 ✦로 둔다.
- 결정(겹침 없애기): 같은 동작을 한 화면에 두 번 두지 않는다. 카드의 더보기는 목록 아래 'N건 더 보기 ›' 한 곳, 메일 읽기 화면 위 답장은 아이콘이고 주 동작은 본문 아래.
- 결정(모양): 업무 완료는 동그라미 체크(마우스를 올리면 흐린 ✓), 여러 건 고르기는 네모 체크. 안 읽은 메일은 이름 앞 파란 점 + 굵은 글씨. 메일 목록의 분류 · 업무 수 · 확인 사유는 회색 한 줄로 잇고 칩으로 늘어놓지 않는다.
- 결정(색, 11-13 문규남): 기한 라벨과 확인 사유 칩의 색은 UX-D10 그대로 둔다(검정 · 파랑 · 초록 · 회색). 색 신호를 줄이는 안(검정 채움 하나만)은 택하지 않았다.
- 결정(긴급 중복 세기, 11-13 문규남): UX-D3의 '긴급 업무도 유형 칸에 같이 보인다'는 그대로 두되, 유형 칸 머리 숫자는 긴급이 아닌 업무만 센다. 같이 보이는 긴급 업무는 '긴급 N건 함께 보임'으로 적는다. 그래서 긴급 + 유형 칸 숫자의 합이 미처리 수와 같다(모의 v2: 긴급 5 + 회신 4 · 요청 3 · 검토 1 · 기타 1 = 14).
- 결정(입력): 에이전트 입력은 테두리 하나 안에 자동으로 늘어나는 입력칸과 둥근 보내기 단추를 둔다. 보내기는 글이 있을 때만 진하다. 대화가 시작되면 소개 · 예시를 숨긴다.
- 결정(확인 방법): 화면을 바꾸는 PR은 헤드리스 브라우저 캡처로 전후를 보고, PR에 붙인다.
- 바뀐 것: UX-D3(유형 칸 숫자), wireframe 13절 `Y1~Y4` · V-6 · V-9 숫자.
- 대안: 기한 라벨을 검정 채움 하나만 남기는 안(Linear · Todoist처럼 먼 기한은 색 없음) — 색으로 기한을 읽는 기존 결정을 유지하기로 해 택하지 않았다.

### UX-D20 · 대시보드: 즐겨찾기 칸 · 카드 안 스크롤 · 오른쪽 위 더보기 · 기한 라벨 빨강 · 초록 · 파랑 (2026-11-14)

### FE-D21 · Ctrl+J(⌘J)로 에이전트 패널을 열고 닫는다 — Ctrl+B는 그대로 메일함이다 (2026-11-13)

- 상태: 일부 대체(`../10_planning/reminders.md` 12.8, 11-15) · 제안: 문규남 · 결정: 문규남(11-13) · 리뷰: [미정] · 공동: — · 근거: UX-D11(Ctrl+B 메일함) · `components.md` 6절(단축키 가드) · 피클의 어디서나 부르는 단축키

- 결정: 설정을 뺀 모든 화면에서 Ctrl+J(맥은 ⌘J)를 누르면 에이전트 패널이 열리고, 다시 누르면 닫힌다. 에이전트 화면에서는 패널을 겹쳐 열지 않고 입력칸으로 포커스를 옮긴다. Ctrl+B는 바꾸지 않고 메일 화면의 메일함 열고 닫기로 남긴다.

- 가드: 다른 전역 단축키와 같은 가드를 거친다. 한글을 조합하는 중(`isComposing` 또는 keyCode 229)이거나 입력칸 · 여러 줄 입력 · 편집 영역에 포커스가 있으면 동작하지 않는다. 한글 자판에서는 key가 'ㅓ'로 오므로 물리 키(`KeyJ`)도 본다. 패널 입력칸 안에서 닫을 때는 Esc를 쓴다.
- 반영: `components.md` 6절 단축키 표, 메일 화면 단축키 도움말(?)에 한 줄, 상단 바 에이전트 버튼의 `aria-keyshortcuts`. 판단은 `lib/shortcuts.ts`의 순수 함수이고 시험이 있다.

### FE-D22 · 에이전트 작업은 작업 카드로 보이고, 끝났을 때 보고 있지 않으면 세 단계로 알린다 (2026-11-13)

- 결정(알림 세 단계): 작업이 끝났을 때 사용자가 그 작업을 보고 있으면 알리지 않는다. 패널이 열려 있거나 에이전트 화면에 있고 탭이 보이는 상태라면 카드가 이미 눈앞에 있기 때문이다. 보고 있지 않으면 ① 앱 안에 토스트 하나를 띄운다. 제목은 결과 제목, 설명은 내가 시킨 말이고, [열기]를 누르면 에이전트 화면으로 가서 그 결과를 오른쪽에 연다. ② 탭이 가려져 있고, 사용자가 에이전트 화면의 '작업이 끝나면 브라우저 알림 받기'를 직접 켰고, 브라우저가 허락했으면 브라우저 알림도 띄운다. 허락은 앱을 열 때 저절로 묻지 않고 그 상자를 켤 때 한 번만 묻는다. 묻지도 않고 권한 창을 띄우면 대부분 거절당하고 다시 묻기도 어렵기 때문이다. ③ 알림 센터(FE-10)에도 한 줄을 남기려 했지만, 지금 알림 센터는 빈 틀이라 항목을 넣을 자리(훅이나 저장소)가 없다. 다른 담당의 영역이라 구조를 바꾸지 않고, 넣을 곳에 TODO 주석(`features/agent/useAgentCompletion.ts`)만 남겼다. 사용자가 스스로 취소한 작업은 알리지 않는다. 알릴지 정하는 판단은 순수 함수(`features/agent/agentNotify.ts`)로 떼어 시험한다.

- 보완(#62 리뷰): 확인 카드를 기다리기 시작한 순간도 같은 기준(보고 있지 않으면 토스트 [열기])으로 알린다. 그동안은 작업이 '진행 중'으로 남아, 패널을 닫으면 5분 뒤 만료 토스트가 처음 알림이었다. 확인 카드 만료는 브라우저 시계로 재므로, 서버 시각(시연 시각 `CLOCK_START`)과 차가 5분을 넘으면 받은 때부터 5분으로 잰다(`localDeadline`). 그동안은 서버가 과거에 있으면 받자마자 만료됐다. 마지막 판정은 서버 409가 한다.

### FE-D23 · 근거 형광펜은 글자 그대로 찾고, 업무 줄 순서를 형광펜 순서에 맞춘다 (2026-11-13)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-13) · 리뷰: [미정] · 공동: AI(AI-15 근거 문장) · BE(`tasks.evidence_text`) · 근거: UX-D16 · design_system 형광펜 · FE-5b(handoff 11-13 4번) · 번호: FE-D20~D22는 #62가 쓴다
- 결정: 근거 문장은 본문 문단에서 글자 그대로 찾는다. 줄바꿈과 겹친 공백만 같은 것으로 보고, 문장 부호 · 낱말이 하나라도 다르면 칠하지 않는다. AI-15가 '본문에 그대로 있는 문장'만 내므로 비슷한 문장을 고쳐 맞추면 오히려 지어낸 근거가 된다.
- 결정(11-14, #73 리뷰): 근거는 '본문 문장을 줄바꿈으로 이은 것'(AI-D14)이므로 줄마다 따로 찾는다. 근거 전체가 한 문단에 그대로 있으면 한 자리로 칠하고, 아니면 줄마다(다른 문단이어도) 찾아 찾은 줄만 칠한다. 업무 줄을 누르면 첫 줄로 옮기고 그 업무의 근거 줄을 모두 진하게 보인다. '근거 문장 없음'은 한 줄도 찾지 못했을 때만 적는다. 처음에는 근거 전체를 한 문단에서만 찾아, 기한 문장이 다음 줄에 붙은 근거(ai `_with_due`)를 실제 서버 본문에서 찾지 못했다.
- 결정: 업무 줄 순서를 본문의 형광펜 순서에 맞춘다(위 업무 = 위 형광펜). 근거를 찾지 못한 업무는 그 뒤에 원래 순서(급한 순)로 둔다. 본문을 받기 전에는 급한 순 그대로다.
- 결정: 형광펜은 늘 칠해 둔다. 업무 줄을 누르면 그 문장으로 굴리고 0.8초 진한 형광펜(`--c-mark-strong`)과 테두리를 보인다. 동작 줄이기 설정이면 굴리기 동작 없이 바로 옮긴다.
- 결정: 근거를 찾지 못한 업무는 업무 줄에 '근거 문장 없음'을 적는다. 완료 · 제외한 업무에는 적지 않는다(끝난 일에 같은 말이 줄줄이 붙어 화면이 지저분해진다).
- 같은 문장(같은 자리)을 근거로 쓴 업무가 둘이면 형광펜 하나를 함께 쓴다. 일부만 겹치는 자리는 함께 쓰지 않고 본문에서 다음에 나오는 같은 글을 찾는다(없으면 그 줄은 칠하지 않는다).
- 남은 일: 대시보드에서 업무를 눌러 메일로 넘어왔을 때 그 문장으로 바로 옮기는 것(UX-D16 두 번째 결정)은 주소에 업무 번호를 싣는 일이 함께 필요해 이번에 하지 않았다.

### UX-D19 · 에이전트 화면은 왼쪽 메뉴 · 가운데 목록 · 오른쪽 상세의 세 칸이고, 🔔 팝업은 새로 온 것만 보인다 (2026-11-14)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-14) · 리뷰: [미정] · 공동: 이재운(알림 센터 리뷰, FE-10 넘겨받음) · 근거: 공통 D57(리마인더 묶음 6개) · `../10_planning/reminders.md` 5 · 6절(PL-18) · `../10_planning/refs/research_reminder_20261113.md` 23 · 24번 · UX-D7 · UX-D12 · UX-D18 · FE-D20
- 결정(세 칸): `#/agent`를 왼쪽 메뉴(약 220px) · 가운데 목록 · 오른쪽 상세의 세 칸으로 바꾸고, 맨 아래에 모든 메뉴가 함께 쓰는 입력 한 줄을 둔다. 메뉴는 리마인더 묶음 여섯 개(기한 · 답 기다림 · 내 약속 · 다시 볼 일 · 준비 · 정리 제안, 묶음마다 건수)와 브리핑 · 회고, 초안, 대화, 기록, 에이전트가 아는 것이다. FE-D20의 '왼쪽 대화 · 오른쪽 결과물' 두 칸은 '대화' 메뉴 안에 그대로 옮겼다. 리마인더가 여섯 묶음으로 늘어나 대화 옆 탭 하나로는 담을 수 없고, 메일 화면이 이미 '메일함 · 목록 · 읽기'의 세 칸이라 같은 읽기 순서를 쓰면 새로 익힐 것이 없기 때문이다.
- 결정(주소): 메뉴와 고른 항목을 주소에 남긴다(`#/agent/reminders/due/<항목 키>`, `#/agent/briefing` 등). 그래서 뒤로 가기가 메뉴 이동과 항목 선택을 되돌리고, 🔔 줄이나 토스트에서 특정 항목으로 바로 들어올 수 있다. 예전 주소 `#/agent`는 리마인더 전체로 바꿔 쓰고, 패널의 [크게 보기]와 작업이 끝났다는 토스트의 [열기]는 대화 메뉴로 간다.
- 결정(아래 입력과 고른 리마인더): 리마인더를 고르면 입력 위에 '고른 리마인더: 제목 ✕'가 붙고, 그 상태에서 보낸 명령에는 그 업무 번호와 항목 키가 함께 간다. "금요일로 미뤄"처럼 대상을 말하지 않아도 무엇을 가리키는지 분명해지기 때문이다. 리마인더 메뉴 안에서는 칩이 오른쪽 상세와 늘 같고, 다른 메뉴로 옮기면 마지막에 고른 항목을 들고 간다. 대화 메뉴가 아닌 곳에서 보낸 명령은 결과가 대화에 쌓이고 지금 화면에는 결과 한 줄 토스트(되돌릴 수 있으면 [실행 취소])만 뜬다. 토스트는 아래 입력을 가리지 않게 입력 위로 올린다.
- 결정(🔔 팝업과 에이전트 메뉴의 나눔): 400px 팝업에는 '지금 새로 온 리마인더 알림'만 최대 5줄 보이고, 전체 정리는 에이전트 화면 리마인더 메뉴가 맡는다. 맨 아래 '리마인더 전체 보기 (N) ›'는 팝업이 길어져도 늘 보이게 바닥에 붙였다. 작은 창에 전체 목록과 거르기를 다 넣으면 어느 쪽도 제대로 쓰기 어렵고, 같은 목록이 두 곳에 있으면 어디서 처리해야 하는지 헷갈리기 때문이다.
- 결정(패널 탭): 에이전트 패널의 '제안' 탭은 '리마인더' 탭이 되어 같은 목록의 앞쪽 3건과 '전체 보기 ›'를 보인다. 제안 카드와 리마인더가 같은 일을 두 이름으로 부르면 사용자가 둘의 차이를 따로 익혀야 하므로 하나로 합쳤다. 실제 서버에 리마인더 API가 아직 없으면 예전 제안 카드를 그대로 보인다.
- 좁은 화면(1024px 미만): 왼쪽 메뉴는 위쪽 고르기 상자가 되고, 목록과 상세는 한 칸씩 보이며 상세 위 ‹ 뒤로가 목록으로 돌아간다.
- 대안: 리마인더를 팝업 안에서 모두 처리하는 방식 — 400px에 여섯 묶음과 근거 문장, 버튼 세 개를 넣으면 줄마다 두세 줄로 길어져 택하지 않았다. 리마인더 전용 화면을 따로 두는 방식 — 리마인더를 고른 채 에이전트에게 말을 거는 흐름이 끊겨 택하지 않았다.
- 위험 · 남은 일: 공통 문서(PRD 화면 목록)의 에이전트 화면 설명 갱신. 새로고침하면 고른 리마인더 칩과 대화가 사라지는 것은 FE-D20과 같다.

### FE-D25 · 리마인더 목록은 업무 하나에 한 줄이고, 실행할 길이 있는 버튼만 그린다 (2026-11-14)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-14) · 리뷰: [미정] · 공동: — · 근거: `../10_planning/reminders.md` 2 · 3 · 5절 · UX-D18 · 공통 D27(행동 레지스트리) · AI-D18(브리핑은 사실만)
- 결정(한 줄 규칙): 한 업무가 여러 유형에 걸리면 정해진 순서에서 앞선 하나만 남긴다. 순서의 맨 앞은 '끝난 것 같아요' · '답장 보냈어요' 같은 정리 제안이다. 이미 끝난 일을 '기한 지남'으로 재촉하면 사용자가 알림을 믿지 않게 되기 때문이다. 기한 몰림처럼 날짜 단위로 묶인 항목은 비교하지 않고 그대로 둔다. 목록은 기한이 이른 순서이고, 기한이 없는 항목은 그 뒤에 생긴 순서로 둔다. 알림을 세 번 보낸 항목은 '조용히 둔 것 N건' 한 곳에 접어 둔다. 메뉴 건수는 서버 건수 대신 화면에 실제로 보이는 항목으로 센다. 숫자와 목록 길이가 다르면 사용자가 무엇이 빠졌는지 찾게 되기 때문이다.
- 결정(색과 글자): 한 줄은 제목과 둘째 줄 '유형 · 이유'(회색)이다. 색 신호는 하나만 쓴다. '기한 지남'이 있을 때 왼쪽 메뉴 '기한' 숫자만 진하게 하고, 유형 이름은 색 없이 회색 글자다. 상세는 이유, 근거 문장(형광펜), 원본 메일, '이 항목 기록'(처음 알아챈 때 · 알림 횟수 · 마지막 알림) 순서다.
- 결정(버튼): 서버가 준 버튼 가운데 화면에서 실행할 길이 있는 것만 최대 3개, 보조 → 주 순서로 오른쪽 끝에 맞춰 그린다. 완료 · 제외 · 미루기는 대시보드와 같은 업무 동작(`useTaskActions`)과 같은 시각 메뉴를 쓰고, 초안 보기는 에이전트 명령으로, 그날 업무(기한 몰림 T13 start = end)는 캘린더 화면의 그날(`/calendar?day=YYYY-MM-DD`)로, 메일 열기는 메일 화면으로, 적용 · 숨김은 새 리마인더 요청으로 보낸다. 실행할 길이 없는 버튼(예: 아직 없는 캘린더 등록)은 그리지 않는다. 눌러도 아무 일이 없는 버튼은 신뢰를 잃게 하기 때문이다. 빨강 채움은 쓰지 않는다. 리마인더 버튼은 모두 되돌릴 수 있는 동작이라 확정 색이 필요 없다(UX-D18).
- 결정(⋯ 메뉴): 내 일 아님(업무가 있는 항목), 이 유형 알림 끄기(끈 유형이면 켜기), 잘못 알아챘어요(AI가 알아챈 유형만)를 둔다. 같은 동작이 버튼에 이미 있으면 메뉴에서 뺀다. 알림을 끈 유형도 목록에는 계속 보인다. 알림만 줄이고 싶은 사람이 일 자체를 놓치지 않게 하기 위해서다.
- 결정(브리핑 · 회고 · 초안): 브리핑 · 회고 메뉴는 아침 · 퇴근 · 주간 세 종류와 날짜를 고르고, 서버가 준 문장과 묶음 목록을 그대로 보인다. 화면이 만드는 문장도 '무엇이 있는지'만 말하고 '~부터 챙기세요' 같은 권유는 쓰지 않는다(AI-D18). 아직 만들 시각이 아니면 언제 만드는지를 알린다. 초안 메뉴는 이 대화에서 나온 회신 초안을 모아 고쳐 쓰고 [복사] · [답장 화면에서 열기]만 둔다. 보내기는 답장 화면에서만 한다(D37 · UX-D5).

- 위험 · 남은 일: 서버가 버튼을 보내지 않는 유형은 버튼 없이 보인다. 버튼 → 실행 길의 표는 순수 함수라 시험으로 지킨다.

- 보완(11-14 검토 · 브리핑 날짜): 브리핑 · 회고의 '오늘'은 서버 시각(시연 시계일 수 있다)으로 정하고, 서버 시각을 받기 전에는 불러오는 중으로 둔다. 브리핑 주소를 바로 열면 브라우저 날짜로 먼저 정해져 시연 날짜와 다른 날(미래)이 열리던 문제를 막기 위해서다. 날짜를 고르기 전에는 늘 서버의 오늘을 따른다. 또 아침 · 퇴근에서 하루 뒤로 간 뒤 주간에서 [다음 주]를 누르면 오늘보다 뒤의 날짜로 넘어가던 것을, 오늘에서 멈추게 고쳤다.
- 보완(11-14 검토 · 포커스): 상세에서 완료 · 숨김 · 적용으로 항목이 목록에서 빠지면 포커스를 그 자리의 다음 줄로 옮긴다(줄이 없으면 목록 제목). 좁은 화면에서 ‹ 뒤로를 누르면 방금 보던 줄로 돌아간다. 다른 메뉴에서 🔔 줄이나 브리핑 줄로 항목을 바로 열면 목록 제목이 아니라 그 항목의 상세 제목으로 간다. 누른 버튼이 화면에서 사라지면 포커스가 문서 맨 앞으로 떨어져 키보드 · 화면 읽기 사용자가 자리를 잃기 때문이다. 항목이 빠진 뒤에도 상세 칸은 '끝났거나 사라졌어요'를 보여 무엇이 일어났는지 알린다.
- 보완(11-14 검토 · 버튼 잠금): 버튼 잠금을 항목마다 따로 둔다. 전에는 한 항목을 처리하는 동안 다른 항목의 버튼을 눌러도 아무 일 없이 무시됐다(🔔 팝업에서 여러 줄을 빠르게 처리할 때). 같은 항목을 같은 순간에 두 번 누르는 것은 화면을 다시 그리기 전에 막는다.

### FE-D26 · 알림 센터(FE-10)를 넘겨받아 만든다 — 🔔 숫자는 안 읽은 리마인더 알림만 센다 (2026-11-14)

- 넘겨받음: FE-10(알림 센터 · 리마인더 토스트 · 🔔 숫자)은 이재운 담당이었지만, 리마인더 화면(FE-16)과 같은 목록 · 같은 버튼을 써야 해서 따로 만들면 두 곳이 어긋나기 쉽다. 그래서 문규남이 넘겨받아 만들고, 원래 담당인 이재운이 리뷰한다. `features/notifications/` 폴더 담당도 함께 바뀐다(`components.md` 8절).

- 결정(토스트): 새 리마인더 알림이 오면 흰 카드 토스트를 띄우고 저절로 사라지지 않게 한다. 닫아도 팝업에 남는다(UX-D7 그대로). 앱을 처음 열 때 이미 있던 알림은 토스트로 띄우지 않는다. 한꺼번에 여러 장이 뜨면 화면을 가리기 때문이다.
- 결정(FE-D22 ③ 마무리): FE-D22에서 자리가 없어 남겨 둔 '작업이 끝났다는 알림을 알림 센터에도 남기기'를 이번에 마쳤다. 토스트를 띄울 때 같은 제목 · 설명으로 알림 탭에 한 줄을 남기므로, 토스트를 놓쳐도 🔔에서 다시 찾을 수 있다. 이 줄은 앱 안에만 있고 새로고침하면 사라진다.
- 위험 · 남은 일: 실제 서버에 리마인더 API가 없으면 리마인더 탭과 🔔 숫자를 비워 두지 않고 숨긴다. 알림 탭의 앱 안 알림은 기기 사이에 이어지지 않는다.
- 보완(11-14 검토): 리마인더 탭과 🔔 숫자는 알림 요청과 리마인더 요청이 모두 서버에 있을 때만 보인다. 알림 요청만 있고 리마인더 요청(BE-12)이 없을 때는 서버 알림을 모두 알림 탭에 둔다. 리마인더 줄을 누르면 에이전트 화면의 그 항목으로 가야 하는데, 그 화면이 없어 대화 메뉴로 엉뚱하게 넘어가던 것을 막기 위해서다. 줄 버튼(완료 · 미루기 · 초안 등)으로 처리하면 그 알림도 읽음으로 바꾼다. 처리한 줄이 안 읽음으로 남아 🔔 숫자가 줄지 않았기 때문이다. [모두 읽음]은 한꺼번에 읽음 요청이 서버에 아직 없으면 안 읽은 알림을 하나씩 읽음으로 바꾼다. 전에는 그때 버튼을 눌러도 서버 알림이 그대로 남았다. 유형 알림 끄기와 브리핑 미루기의 [실행 취소]가 실패하면 오류 토스트를 띄운다.

### FE-D27 · 리마인더 API는 BE-12 응답 이름을 따르고, 모르는 유형은 그 항목만 뺀다 (2026-11-14)

- 상태: 채택 · 제안: 문규남 · 결정: 문규남(11-14) · 리뷰: [미정] · 공동: BE-12 담당(계약 맞추기) · 근거: `../10_planning/reminders.md` 7.2절 · `components.md` 5.1 · FE-D16(서버 데이터)
- 결정(요청): 리마인더 목록, 숨김 · 신고, 적용, 유형 알림 끄기, 브리핑, 알림 모두 읽음의 여섯 요청을 더했다. 백엔드(BE-12)와 같은 명세로 함께 만드는 중이라 프론트는 명세 7.2절 형식의 모의 응답(이번 단계 유형 15가지를 한 건 이상 넣은 자료)으로 먼저 만들었다. 실제 모드에서 요청이 404 · 405 · 501이면 '없는 기능'으로 보고 그 화면 부분을 숨긴다. 다른 기능과 같은 규칙이다.

- 결정(모르는 값): 서버가 프론트가 모르는 유형을 보내면 그 항목만 목록에서 뺀다. 새 유형이 생겨도 목록 전체가 깨지지 않게 하기 위해서다. 묶음이 틀리거나 없으면 유형으로 묶음을 정한다. 알림의 유형 · 묶음이 모르는 값이면 비워 둔다.
- 결정(명령): 고른 리마인더가 있으면 에이전트 명령 본문에 `task_ids`와 `reminder_key`를 더한다. 고르지 않았으면 이 칸을 보내지 않는다.
- 위험 · 남은 일: (해결, BE-18 #243) 서버가 `task_ids`를 읽는다. 규칙은 서버 · 모의가 같다: 말에 보낸 사람 · 분류 · 낱말이 없으면 고른 업무만 대상(기간 · 메일 조건은 보지 않음. 단 조회는 기간을 말하면 그 기간으로 찾음, #243 리뷰), 대면 고른 업무는 쓰지 않는다. `reminder_key`는 기록용.
- 보완(11-14 · BE-12가 더하는 칸): 브리핑 응답의 `scheduled_at`(그 브리핑을 만들기로 정한 시각)과 항목의 `last_notified_at`(마지막으로 알린 시각)을 선택 칸으로 읽는다. BE-12는 브리핑을 요청할 때 만들기 때문에, 예정 시각 전에 불러도 그때까지의 내용을 보낸다. 그래서 서버가 답한 시각(`as_of`)이 `scheduled_at`보다 이르면 내용이 와도 보이지 않고 "아직 만들 시각이 아니에요. 퇴근 회고는 11/6(금) 17:30에 만들어요."라고만 알린다. 미리 만든 내용을 보이면 퇴근 전에 '오늘 끝낸 일'이 덜 찬 채로 보여 사실과 다르게 읽히기 때문이다. 판단은 브라우저 시계가 아니라 서버 시각으로 한다. `scheduled_at`이 없는 응답은 예전처럼 내용으로 정한다. `last_notified_at`은 상세 '이 항목 기록' 줄의 '마지막 …'에 보이고, 없으면 그 부분을 뺀다. 모의 서버도 두 칸을 같은 이름으로 보낸다.

- 결정(누르기): 한 번 누르면 듣고, 다시 누르면 멈춘다(누름 상태를 화면 읽기에도 알린다). 길게 누르고 있는 방식은 쓰지 않았다. 키보드 · 화면 읽기 사용자가 쓰기 어렵고, 명령은 한두 문장이라 말을 멈추면 5초 뒤 스스로 끝나는 편이 손이 덜 가기 때문이다. 아무리 길어도 60초에서 끊는다. 듣는 중 Esc는 듣기만 멈추고, 듣기가 끝난 뒤의 Esc는 원래대로 패널을 닫는다.

- 결정(글자 흐름): 말하는 동안 글자가 입력칸에 바로 써진다. 듣기 전에 써 둔 글이 있으면 그 뒤에 한 칸 띄워 붙인다. 끝나면 입력칸으로 포커스를 돌리고 커서를 글 끝에 둔다. 보내기는 자동으로 하지 않는다. 음성인식이 이름 · 숫자를 틀리게 받아 적을 수 있어서, 사람이 한 번 보고 고친 뒤 Enter로 보내는 편이 안전하다(D37 '확인은 사람이'). 듣는 중에 사용자가 직접 글을 고치거나 보내면 듣기를 바로 끊고 뒤늦게 온 글자는 버린다. 보낸 칸이 다시 채워지는 일을 막기 위해서다.
- 결정(실패 문구): 이유와 할 일을 안내 줄 한 곳에 쓴다. 권한 거부, 마이크 없음, 말소리 없음, 인터넷 끊김, 보안 연결이 아닌 주소(http)의 다섯 가지를 따로 알린다. 마지막은 공유 서버 IP로 개발 서버를 열 때 크롬이 묻지도 않고 막는 경우라 이유를 따로 적었다. 다시 하려면 🎤를 한 번 더 누르면 된다. 글을 쓰기 시작하면 안내는 원래 키 안내로 돌아간다. 화면 문구에는 그림 문자(🎤)를 쓰지 않는다. 글꼴에 따라 네모로 깨졌다.
- 결정(개인정보): 🎤 말풍선에 "말한 소리는 브라우저 회사 서버에서 글자로 바뀔 수 있어요"를 적는다. 크롬은 소리를 구글 서버로 보내 글자로 바꾸므로, 쓰기 전에 알 수 있어야 한다(기획 detail 1.2절 '음성' [결정 필요]는 그대로 남는다).
- 결정(바꿔 끼우기, D29): 화면은 '어댑터' 약속(`features/voice/stt.ts`)만 알고, 브라우저 방식은 `adapters/browserStt.ts`에 있다. `VITE_STT_MODE=server`면 서버 방식을 고르는데, 서버 음성인식(AI-8 · `/voice/stt`)이 아직 없어서 지금은 🎤를 숨긴다. 서버가 생기면 같은 약속을 따르는 어댑터 하나만 더하면 된다.
- 위험 · 남은 일: 실제 마이크 · 실제 크롬 음성인식으로는 확인하지 못했다(서버에 마이크가 없음). 가짜 음성인식을 심은 헤드리스 브라우저로 누르기 · 글자 · Esc · 실패 · 동작 줄이기 20가지를 확인했다. 시연 전에 크롬에서 https 또는 localhost 주소로 한 번 말해 봐야 한다.
- 보완(#91 리뷰): 크롬이 `start()`를 거절하면(이미 듣는 중인 인스턴스 등) 오류 · 끝을 세션을 돌려준 뒤에 알린다. 그동안은 화면이 자기 세션의 알림으로 받지 못해 '듣는 중'에 멈출 수 있었다. 함께 챙길 일 두 가지: ① http IP 주소에서는 마이크가 막히므로 시연 주소를 https로 정하는 일(인프라, INF-11 배포 서비스 선정과 함께), ② 브라우저 방식은 소리가 구글 서버로 간다. 기획 detail 1.2절 '음성' [결정 필요]를 IR 전에 정한다(멘토링 개인정보 지적과 같은 맥락). 정하기 전까지는 🎤 말풍선의 안내 문구로 알린다.

## FE-D10 · FE-1 대시보드 임시 집계 기준 (2026-11-05)

- 상태: 제안(FE-1 구현 선택 · BE-3에서 맞출 기준) · 제안: 임동하 · 결정: [미정] · 리뷰: [미정] · 공동: — · 근거: 구조도 5절 · D20 · D39 · D40 · `backend/scripts/demo_expected.py`

## FE-D14 · '미처리' 건수는 나중에를 포함하고, 대시보드 조회는 15초에서 끊는다 (2026-11-12)

- 결정(문구): 기한 지남 카드 제목의 ⚠를 뺀다(UX-D10 · D11, D20-3 ⚠ 칩 대체). 설명은 실제 기준대로 "미처리 업무(나중에 제외) 중 기한이 기준 시각보다 앞선 것". 완료율 설명은 식을 바꾸지 않고 "완료 ÷ (미처리 + 완료)"로 고쳐 쓴다(미처리에 나중에가 들어가므로 같은 값).
- 결정(제한 시간): FE 대시보드 조회(`frontend/src/api/httpClient.ts`, `GET /dashboard`)는 15초(`REQUEST_TIMEOUT_MS`)에서 끊는다. 화면 쪽 취소 신호와 제한 시간 신호를 함께 건다. 제한 시간 초과는 헤더를 기다리는 중이든 본문(`res.json()`)을 읽는 중이든 `NetworkError`로 올리고(계약 오류로 위장하지 않음), 화면 문구는 기존 "서버에 연결하지 못했습니다"를 쓴다(`errors.ts` · `errorText.ts` 변경 없음). 화면 쪽 취소는 `NetworkError`로 바꾸지 않고 그대로 올린다.

- 대안: 미처리를 `pending`만 두고 나중에를 따로 보이기(FE-D10, UX-D2와 다름). 제한 시간 초과를 별도 오류 종류 · 문구로 나누기(`errors.ts` · `errorText.ts`를 고쳐야 해 이번에 하지 않음).
- 위험 · 남은 일: 상태 변경 요청(#48 `frontend/src/api/actions.ts`)은 따로 `fetch`를 써서 이 제한 시간이 걸리지 않는다 → #48 병합 후 맞출 후속 작업. 15초는 BE-3 실제 응답 시간을 재 본 값이 아니다(시연 데이터 기준 넉넉히 잡음).
- FE-13 구조로 옮기며 바뀐 점(2026-11-13, 결정: 문규남 · #51 내용을 새 화면 기반에 옮김): ① 미처리 건수는 FE-3 `features/tasks/aggregate.ts`의 N1(미처리 = 미처리 + 나중에)에 이미 들어 있어 옮기지 않았다. ② 제한 시간은 대시보드 한 곳이 아니라 `api/httpClient.ts`의 공통 `request()`에 걸어 모든 요청에 적용한다. 위 '위험'에 적은 상태 변경 요청(완료 · 되돌리기 · 일괄)도 같은 함수를 지나므로 이제 함께 끊긴다. ③ 모델을 부르는 요청(에이전트 명령 · 메일 요약)과 메일 보내기는 140초(`SLOW_REQUEST_TIMEOUT_MS`)를 쓴다. backend가 ai를 130초까지 기다리므로(`backend/app/ai_client/client.py` `TIMEOUT_S`), 15초로 끊으면 모델이 조금만 늦어도 화면이 먼저 '연결 실패'를 띄우고 backend가 정한 503 안내("지금은 명령을 처리할 수 없어요")를 받지 못한다. 메일 보내기는 중간에 끊으면 보냈는지 알 수 없게 되므로 같이 길게 둔다.
