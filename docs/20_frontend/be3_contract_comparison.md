# BE-3 대시보드 API 계약 비교 (구조도 8절 vs FE-1 임시 형식)

> 상태: 미결 비교표 — 계약을 정한 문서가 아니다 · 작성: 임동하(FE-1) · 결정: [미정] · 리뷰: [미정] · 갱신: 2026-11-05
> 비교 대상: `docs/00_common/architecture.md` 8절 API `[제안]` ↔ `frontend/src/api/provisional.ts`(FE-1 임시 가정)
> 관련 FE 결정 제안: `decisions.md` FE-D10(임시 집계 기준)

## 0. 진행 순서

1. 이 표를 FE · BE가 함께 보고 항목별로 계약을 정한다(구조도 8절 갱신 또는 `backend/app/schemas` 정의).
2. **BE-3는 이 비교를 바탕으로 계약을 결정한 뒤 구현한다.**
3. FE는 정해진 계약에 맞춰 `frontend/src/api/`의 `provisional.ts` · `adapter.ts` · `httpClient.ts`만 바꾼다. 화면 코드는 화면용 모델(`types.ts`)만 쓰므로 그대로 둔다.

이 문서는 어느 쪽 안도 확정하지 않는다. backend는 구현하지 않았다.

## 3. 칸 배정 기준의 실제 결과 — 업무 문장에 다른 칸 이름이 포함된 사례

> 현재 규칙(업무가 나온 **메일의 `category`**로 업무 성격 칸을 정함, `tasks`에는 분류 칸 없음)을 모의 데이터 v1(`frontend/src/api/mock/dashboard.v1.json`, 기준 시각 2026-10-20T09:00 KST, 업무 62개)에 적용한 결과다. 분류가 틀렸다는 판정이나 오분류율이 아니라 현재 규칙대로 배정된 결과를 글자 기준으로 모은 것이며, **BE-3에서 이 규칙을 유지할지(메일 단위) 업무 단위 분류를 둘지 결정할 항목**이다. FE 코드는 바꾸지 않았다.

- 판정 기준: 업무 문장(`tasks[].text`)에 **배정된 칸이 아닌 다른 칸 이름**(회신 · 요청 · 검토 · 기타 중 하나)이 글자 그대로 들어 있으면 '업무 문장에 다른 칸 이름이 포함된 사례'로 센다. 뜻을 해석하지 않은 단순 글자 포함 기준이다.
- 결과: 업무 62개 중 **10개**(메일 9통). 배정 칸 '요청'인데 문장에 '회신' 8개, 배정 칸 '검토'인데 문장에 '회신' 2개. 그 밖의 조합은 0개.
- 예: "팀 주간보고를 양식에 작성해 회신"(M-0007)은 문장에 '회신'이 있지만 소속 메일의 category가 요청이라 '요청' 칸에 들어간다.

- 회신 칸의 정의(문서 확인 결과): 세 문서가 모두 **메일 단위**로 정의하고 서로 충돌하지 않는다.
  - `docs/00_common/decisions.md` D39: 회신요청 → 회신(묶음은 `[제안]`).
  - `docs/00_common/architecture.md` 4절 분류 묶음 `[제안]`: 회신 = 행동 유형 '회신요청'.
  - `docs/50_data_eval/label_guide.md` 2절: 회신요청 = "의견 · 답 · 확인 결과 · 가부를 회신해 달라". 자료 · 문서를 만들어 보내 달라는 자료제출요청(→ 요청), "참석(또는 참석 여부 회신)"은 일정참석(→ 요청), 검토 · 결재는 검토승인요청(→ 검토).
  - 위 정의대로면 10건 모두 메일의 주 유형에 따라 배정된 것이다(예: 참석 여부 회신 → 일정참석 → 요청).
  - **BE-3 확인 필요**: (1) 묶음 매핑 자체가 `[제안]` 상태다. (2) 업무(할 일) 단위의 칸 정의는 어느 문서에도 없다 — 화면에서 업무 문장의 '회신'과 칸 이름 '회신'이 다른 뜻으로 읽힐 수 있다. (3) 행동 유형 '회신'(내 요청에 대한 상대의 답)은 '기타'로 묶여 칸 이름 '회신'과 이름이 겹친다.
- 결정할 것: (가) 메일 단위 유지 — 지금 규칙, 저장 칸 변경 없음 / (나) 업무 단위 분류 칸 추가 — `tasks`에 분류 칸 · ai `/classify` 응답 형식 변경 필요(AI · BE 합의).

## 4. 응답 정합성 전제와 FE 방어 처리 (2026-11-07, #18 리뷰)

> **FE 전제(계약 후보)**: BE-3에서 확정할 항목이며 지금은 FE 임시 가정이다.
> 1. 참조 완전성: 대시보드 응답(`DashboardSource`)의 `mails[]`에는 `tasks[]`가 가리키는 메일(`mail_id`)이 **모두** 들어 있다. 현재 FE는 이 전제로 동작한다.
> 2. ID 유일성: **메일 목록 안에서 `mail.id`가 유일하고, 업무 목록 안에서 `task.id`가 유일하다.** 두 목록 사이는 따로 본다 — `mail.id = 1`과 `task.id = 1`이 함께 있어도 된다(`aggregate.ts`는 목록별로 따로 검사, `aggregate.test.ts`).

| 상황 | FE-1 처리 | 성격 |
|---|---|---|
| 메일 목록 안 `mail.id` 중복, 또는 업무 목록 안 `task.id` 중복 | `ContractError` → 대시보드 오류 화면('받은 데이터를 화면에 표시할 수 없습니다') | 계약 위반 |
| 업무가 가리키는 메일이 `mails[]`에 없음 | 대시보드는 그대로 그린다. 해당 업무는 '메일 정보 없음'으로 유지하고(상태 · 기한 그대로), 상태 · 기한으로 세는 집계 · 기한 칸에는 넣고 상급자 · 즐겨찾기 · 업무 성격 칸에는 넣지 않는다(분류 · 발신자를 지어내지 않음). 화면 위에 '메일 정보를 불러오지 못한 업무 N건'(N = 영향받은 고유 업무 수, 제외 상태 빼고)과 '메일 정보 확인 필요' 목록, 관련 열에 '분류 · 발신자별 집계에 반영되지 않았습니다' 안내 | **계약 위반에 대한 방어 처리** — 불완전한 응답을 정상 계약으로 허용한다는 뜻이 아니다 |

- 방어 처리를 고른 이유: 메일 하나가 빠졌다고 다른 업무까지 모두 안 보이면 누락 방지(D13) 목적에 어긋난다. 대신 빠진 것을 숨기지 않고 화면에 알린다.
- 원본 보기 · 답장처럼 메일 정보가 필요한 동작은 FE-1에 아직 없다. 생기면(FE-5) 메일 정보 없는 업무에서는 막고 이유를 보여 준다.
- **BE-3 협의 항목**: 메일 · 업무를 각각 페이지로 나누거나 필터를 걸면 참조 완전성 전제가 깨질 수 있다.
  - 정할 것 ① 집계 위치: 칸 · 숫자를 서버가 집계할지, 지금처럼 FE가 집계할지.
  - 정할 것 ② 메일 정보 확보: **서버 집계 여부와 별개로, 화면에 표시할 업무에 필요한 메일 정보(발신자 · 분류 · 제목 등)는 응답에 함께 제공하거나 합의된 조회 경로로 확보한다.** 서버가 숫자를 집계해 줘도 업무 카드에 그릴 메일 정보 문제는 그것만으로 해결되지 않는다.
  - 현재 FE는 `DashboardSource`에 참조 메일이 모두 들어 있다는 전제로 동작한다. 업무에 메일 정보를 붙여 보내기 · 메일을 따로 조회하기 등 다른 방식을 채택하면 BE-3에서 계약과 FE 구현(`provisional.ts` · `adapter.ts` · `aggregate.ts`)을 함께 바꾼다.
  - 백엔드 계약 · API는 이 문서에서 정하지 않는다.
